## 第 0 章　角色与任务定义

### 0.1 你被要求扮演的角色

你是一名兼具**图形工程**与**科学可视化**经验的前端工程师。你不写演示级别的「能跑就行」的代码，而是写**在普通笔记本上双击即可运行、且经得起近看**的代码。你同时具备天文学常识，知道银河系不是一团随意的雾，太阳不是随便摆的一个点，行星的自转方向、光环倾角、轨道顺序都是有出处的。

你的工作不是从零发明一个新项目，而是在**已有的单文件实现**上继续演进。任何新增功能都必须先证明它不会破坏已有的三条底线：

1. 双击 `index.html` 就能打开，不依赖网络、不依赖构建、不依赖任何外部资源；
2. 从银河全景一路放大到行星特写，全程不出现黑屏、闪白、跳帧式的尺度突变；
3. 鼠标、触摸、键盘三种输入下，视角控制的行为一致且可预期。

### 0.2 任务的三层结构

本提示词分三层，三层都要读完才能动手：

- **第一层：现状规格（第 1 至第 8 章）**——已经实现的系统长什么样，常量是多少，算法怎么走。这一层的作用是防止你在改一个局部时，无意中破坏另一处的隐含约定。
- **第二层：演进规格（第 9 至第 14 章）**——交互、界面、性能、可访问性、测试的完整要求，其中有一部分已经落地，有一部分是**本次要补的**。
- **第三层：实施规格（第 15 至第 29 章）**——分阶段路线图、本次交付范围、禁止事项；其后各章为实施辅助（数学推导、着色器注释、调参、调试、走查、性能、天文背景、数据规范、发布流程、FAQ、术语表），按需查阅。**当第一层与第二层冲突时，以第二层为准；当第二层与第三层冲突时，以第三层为准。**

### 0.3 判断「做完了」的标准

不是「代码能跑」，而是下面五条同时成立：

1. **可看**：首屏三秒内出现可辨认的旋涡结构，而不是一片噪点；
2. **可动**：绕转、平移、缩放三种操作互不打架，操作后画面不会「弹回去」；
3. **可达**：从银心到任意一颗行星，最多四次点击就能抵达，且每一次都有连续的运动过渡；
4. **可信**：面板里的数字与文本经得起查，不出现编造的卫星数量、错误的公转周期；
5. **可退**：任何一层都能用一次明确的操作退回上一层，用户不会「迷路」。

### 0.4 本项目的非目标

明确写下来，避免范围蔓延：

- 不做真实星表渲染（Gaia / Hipparcos 数据接入）；
- 不做物理引擎（轨道用解析解，不做 N 体引力积分）；
- 不做多人、不做云端、不做账号；
- 不做移动端原生封装（Web 端触摸可用即可）；
- 不追求「照片级真实」——目标是**可读的、有层次的、经得起近看的结构化示意**，取舍标准是「是否帮助用户理解尺度与位置关系」。

## 第 1 章　产品定位与体验目标

### 1.1 一句话定位

一个**从银河系整体一路放大到单颗行星表面细节**的连续尺度浏览器；它用程序化生成换取零资源依赖，用一条连续的相机路径换取「同一次浏览」的空间感，用一屏信息面板换取「看完还想知道为什么」。

### 1.2 用户的三种典型路径

**路径 A：好奇型（占多数）**

打开 → 看到旋涡在慢慢转 → 拖动鼠标换个角度 → 发现滚轮能放大 → 一路推进到银心附近 → 自动掉进太阳系 → 被行星排成一列的画面震住 → 点地球 → 读一段历史 → 关掉。

这条路径上的关键指标是**首次「啊哈」时刻出现的时间**。当前设计把它压在了「拖动一下」和「滚一下」两个动作之内，任何新增的加载步骤、任何需要读说明才能开始的交互，都会破坏它。

**路径 B：对照型**

已经知道地球直径 12742 公里，想验证这个模型有没有把木星画得太大。他会点开木星、比对数字、回到太阳系、看轨道间距。这条路径要求**数字准确**、**等比关系可解释**、**面板不遮挡要看的对象**。

**路径 C：教学型**

要把这个页面投到教室大屏上讲解。此时需要：字号够大、配色在投影仪上不糊、能暂停、能隐藏所有 UI 只留画面、能一键复位。这条路径直接决定了第 9 章里「演示模式」的必要性。

### 1.3 三条体验红线

1. **不许有黑场遮罩**。层与层之间只能用透明度交叉溶解 + 相机补间，不允许用全屏黑幕「盖住加载」。黑场会让用户觉得自己被中断了，而不是自己在移动。
2. **不许有尺度跳变**。当相机半径跨越某个数量级时，物体的屏幕尺寸变化率必须连续。做法是把「视觉半径」而非「真实半径」作为渲染尺度（见 6.3 节）。
3. **不许有死胡同**。「返回银河」按钮的可点区域必须始终存在，即使在聚焦某颗行星、面板展开、UI 折叠的最坏组合下也不能被遮挡或失效。

### 1.4 视觉基调

- **背景**：近黑，但不是纯黑（`#05070d` 量级），留一点冷调，避免 OLED 屏上的「黑洞感」；
- **银河**：核心偏暖（米白 → 淡金），旋臂偏冷（青白 → 淡蓝紫），暗尘带必须是**吸收**而不是「画上去的深色」；
- **太阳系**：行星颜色取「肉眼/望远镜下的印象色」，不是光谱反照率的物理换算值；
- **UI**：半透明玻璃面板，边框 1px 低对比，正文对比度不低于 4.5:1，标题不使用纯白（用 `#e8eefc` 一类）；
- **动效**：所有补间默认 900–1700 毫秒，缓动统一用 `easeInOutCubic`，禁止线性匀速的长距离移动（会显得机械）。

## 第 2 章　硬约束

### 2.1 零依赖

以下全部**禁止**：

- 任何 CDN 引用（`three.js`、`d3`、`gsap`、字体服务、图标库）；
- 任何 `<img>` / `<link rel="stylesheet" href="...">` 外部资源；
- 任何构建步骤（webpack / vite / rollup / tsc / babel）；
- 任何 ES Module 的 `import`（`file://` 协议下 `type="module"` 会因 CORS 失败，这是本项目历史上踩过的坑，见 2.5）。

允许的做法：

- 内联 `<style>` + 内联 `<script>`；
- Canvas 2D 生成的纹理回退（Firefox 极老版本无 WebGL 时）；
- 系统字体栈（`-apple-system, "Segoe UI", "Noto Sans SC", "Microsoft YaHei", sans-serif`）。

### 2.2 单文件

交付物是**一个 `index.html`**。文档、许可证、测试脚本可以放在仓库里，但运行本体必须是一个文件。这条约束的意义在于：用户可以把文件发微信、丢 U 盘、双击打开，不需要**任何**解释。

新增功能时，如果它需要第二份文件才能工作，那么它就不属于 P0/P1，只能放到 P3 的「增强版」分支里。

### 2.3 语法下限

- 不使用可选链 `?.`、空值合并 `??`、`Array.prototype.at`、顶层 `await`；
- 不使用类字段、私有字段；
- 允许：`let/const`、箭头函数、模板字符串、`Map/Set`、`Float32Array`、`PointerEvent`（带降级）。

理由：本文件的预期使用者可能在任何浏览器里打开它，包括某些企业的内嵌浏览器。语法错误会导致整页白屏，而白屏没有任何提示。

### 2.4 编码与兼容

- 文件必须是 **UTF-8 无 BOM**；
- 所有中文文案**直接写在文件里**，不做转义；
- WebGL 上下文优先 `webgl2`，失败回退 `webgl` / `experimental-webgl`；
- `EXT_texture_filter_anisotropic` 只做「有就用、没有就算了」的可选增强；
- 移动端必须 `viewport-fit=cover`，并给底部工具栏留 `env(safe-area-inset-bottom)`。

### 2.5 历史踩坑记录（不可重犯）

1. **CDN + `file://` + ES module**：早期版本引用了 CDN 上的 Three.js，并用 `type="module"`。结果在离线和 CORS 限制下直接白屏，且没有任何错误提示。这是本项目从「能用 Three.js 就用」转向「零依赖原生 WebGL」的直接原因。
2. **核球调参导致暗环**：为了让银心更亮，曾经把 `bulge` 的指数系数调到过高，结果核心出现一圈比周围更暗的环（因为归一化后中间过曝、外侧被压）。教训是：**任何发光体的累加都要做软饱和（`1 - exp(-x)`），不允许裸加**。
3. **补间回调注册顺序**：`tweenCam()` 函数开头会清空 `camTweenDone` 数组。如果先 `push` 回调再调 `tweenCam()`，回调会被清掉。**必须先调用 `tweenCam()`，再 push 回调。**
4. **无头截图陷阱**：用 `--virtual-time-budget` 截首屏时，启动期约 2.3 秒的纹理同步生成会吃掉虚拟时间预算，截图会落在第一到第三帧。验证交互必须用「强制补间收尾」的确定性测试，而不是靠等时间。

## 第 4 章　数学与坐标系

### 4.1 坐标约定

- 右手系，**Y 轴向上**为默认，但在银河盘面（`y = 0`）上进行拾取时，视线接近水平会退化为「用 Z 轴向上」的备用参考（见 7.6）；
- 银河盘面位于 `y = 0` 平面，厚度方向为 Y；
- 太阳系同样使用 XZ 平面作为轨道面，行星在 `y ≈ 0` 附近带微小轨道倾角；
- 角度单位：**内部一律弧度**，仅 UI 展示时转成「度」。

### 4.2 矩阵约定

列主序（与 WebGL 一致），平移分量位于 `m[12..14]`：

```
| m0  m4  m8   m12 |
| m1  m5  m9   m13 |
| m2  m6  m10  m14 |
| m3  m7  m11  m15 |
```

`M4.multiply(o, a, b)` 计算 `o = a · b`，并允许 `o` 与输入共享引用（内部使用临时数组 `M4._t` 后再拷贝）。**注意**：这意味着 `multiply` 不是可重入的，禁止在同一个表达式里嵌套调用。

`M4.normalMat3(out, m)` 取左上 3×3 并按列归一化，用于法线变换。因为本项目的模型矩阵只包含**均匀缩放 + 旋转 + 平移**，不需要严格意义上的逆转置。

### 4.3 投影与视图

- `perspective(fovy, aspect, near, far)`：`fovy = 55°`，`near = 0.5`，`far = 50000`。
- 近平面 0.5 与远平面 50000 的比例为 1:100000，深度精度在中远距离会明显退化。因此**所有近景物体（行星、环、轨道线）必须绘制在照相机附近**：太阳系层在进入时会把相机半径拉到 360 量级，而不是在 3600 的距离上继续画行星。
- `lookAt(eye, center, up)` 在相机极角接近极点（`phi < 0.12` 或 `phi > π-0.12`）时，把 `up` 从 `(0,1,0)` 切换为 `(0,0,1)`，避免万向节附近的画面翻转。切换阈值必须与 `camBasis()` 中的判断**完全一致**，否则会出现「相机上方向」与「平移基向量」不一致的错位感。

### 4.4 阻尼

所有相机参数都用**指数阻尼**，而不是固定插值系数：

```js
var damp = 1 - Math.exp(-dt * 11);
cam.theta  += (cam.tTheta  - cam.theta)  * damp;
cam.phi    += (cam.tPhi    - cam.phi)    * damp;
cam.radius += (cam.tRadius - cam.radius) * damp;
```

理由：固定系数在 60fps 与 144fps 下的响应速度不同，交互手感会随显示器刷新率变化。指数形式在数学上等价于「一阶低通滤波器」，与帧率解耦。

`dt` 必须截断到 `0.1s`，否则切回标签页时会因为巨大的 `dt` 让画面瞬移。

### 4.5 缓动

```js
function easeInOutCubic(t) { return t < 0.5 ? 4*t*t*t : 1 - Math.pow(-2*t + 2, 3) / 2; }
function easeOutCubic(t)  { return 1 - Math.pow(1 - t, 3); }
```

补间的**时长**按用途区分：层切换 `1700ms`，聚焦 `1200ms`，点击推进 `900ms`，提示气泡 `900ms` 后自动消失。禁止把补间时长做成随机值。

### 4.6 噪声

```js
function hash2(x, y, s) {
  var h = Math.imul(x|0, 374761393) ^ Math.imul(y|0, 668265263) ^ Math.imul(s|0, 1274126177);
  h = Math.imul(h ^ (h >>> 13), 1274126177);
  return ((h ^ (h >>> 16)) >>> 0) / 4294967296;
}
```

`valueNoise` 用双线性 + smoothstep 插值；`fbm` 做 4–5 个八度，每层频率 ×2、振幅 ×0.5，最后按总振幅归一化到 `[0,1]`。

关键要求：**同一个 `seed` 必须永远产生同样的纹理**。禁止在任何纹理生成路径里调用 `Math.random()`（粒子分布可以用 `Math.random()`，因为它们不需要可复现）。这条规则的目的是让截图对比、回归测试、缓存复用都成立。

## 第 5 章　银河层的生成

### 5.1 为什么是「三层叠加」而不是「一个模型」

银河层由三种物理性质完全不同的东西组成，用同一种技术画都画不好：

| 组成 | 性质 | 技术选择 |
|---|---|---|
| 盘面的整体辉光 | 连续、平滑、大尺度 | 一张贴在平面上的纹理 |
| 个体恒星与星云 | 离散、点状、数量巨大 | 点精灵粒子 |
| 暗尘带 | **吸收**而非发光 | 反向减法混合的粒子 |
| 远景星空 | 不参与星系旋转 | 独立的点精灵缓冲 |
| 球状星团 | 局部高亮团块 | 面向相机的公告板 |

如果只用粒子，三十四万颗点即使再密，在远景下也会呈现「颗粒感」而不是「辉光」；如果只用纹理，放大后会变成一张糊掉的图。两者叠加，纹理负责「整体形状与明暗」，粒子负责「近看时的颗粒与层次」，这才是可用的组合。

### 5.2 对数螺旋的数学形式

四条旋臂的骨架为：

```
r(θ) = a · e^(b·θ)
```

取 `a = 60`（世界单位），`b = 0.28`。反向使用：

```
θ(r) = ln(r / a) / b
```

第 `k` 条臂的相位为 `phase_k = 2πk / armCount`，`armCount = 4`。

在纹理生成与粒子生成里，判断「某点离旋臂有多近」时，不要做点到曲线的距离计算（太慢），而是取该点的方位角 `th`，算出该半径处旋臂所在的方位角 `armTheta = θ(r)`，求差：

```js
var diff = th - armTheta;
var armMask = Math.pow(Math.max(0, Math.cos(diff * arms)), 2.6);
```

`cos(diff·arms)` 在一条臂附近取 1，在两条臂之间取 −1；截断到 0 之后取 2.6 次方，得到一条「中间宽、边缘陡」的臂状分布。这个指数决定了旋臂的锐利程度：太小则臂与臂连成一片，太大则变成四条细线。**2.6 是经过多次对比后确定的值，修改它需要重新看一遍全景截图。**

叠加噪声扰动：

```js
var n1 = fbm(x * 0.0016, z * 0.0016, 7, 4);
armMask = Math.pow(Math.max(0, Math.cos(diff * arms + (n1 - 0.5) * 2.6)), 2.6);
```

扰动幅度 2.6 弧度是一个经验值：它足以让旋臂「长出毛边」，又不会把臂的位置整体推走。

### 5.3 盘面纹理（`buildGalaxyRows`）

**分辨率**：`2048 × 2048 × RGBA = 16 MB` 的 `Uint8Array`。生成时间在普通笔记本上约 2.2 秒，因此必须分批。

**批处理**：每次处理 32 行，然后 `setTimeout(step, 0)` 让出主线程，总批次 64 次。进度条按 `row / size` 更新。**不允许**一次性生成，否则页面会卡死约 2 秒，用户会以为打不开。

**世界坐标映射**：

```
scale  = (size / 2) / (R * 1.06)      // 像素/世界单位
x      = (px - size/2) / scale
z      = (py - size/2) / scale
```

`1.06` 是留白系数，让星系边缘不会正好卡在纹理边界上（否则 mipmap 边缘会出现一圈发黑的框）。

**每个像素的亮度构成**：

1. **核球项**：椭圆指数衰减
   ```js
   var bulge = Math.exp(-(bx*bx + bz*bz) * 2.0);  // bx = x/(R*0.175*1.38), bz = z/(R*0.175*0.90)
   ```
   X 方向拉长 1.38 倍、Z 方向压短 0.90 倍，形成中央棒状结构。

2. **银盘项**：`disk = exp(-t * 2.55)`，其中 `t = r / R`。指数决定盘面从中心到边缘的衰减速度，2.55 对应「中心亮、外围逐渐变淡但不会突然截断」。

3. **旋臂项**：`armMask`（见 5.2），并乘以 `armFade = smoothstep(0.055, 0.235, t)`。**银心区不画旋臂**——真实星系的棒/核球内部没有明显的螺旋结构，硬画会在中心形成「风车状」，一眼假。

4. **暗带项**：`dustMask`，取比旋臂相位**超前**约 0.95 弧度的位置，指数 1.5（`dc * sqrt(dc)`）。暗带总是位于旋臂内侧前缘，这是密度波理论的直接推论：气体在进入旋臂时被压缩形成尘埃带。

**总亮度**：

```js
var lum = disk * 0.24 + armMask * 0.86 + bulge * 0.95;
lum *= (1 - dustMask * 0.55);          // 尘埃吸收
var e = 1.0 - Math.exp(-lum * 1.55);   // 软饱和
```

软饱和不能省。亮度是几十项叠加出来的，如果直接映射到 0–255，中心会全部裁死成纯白，从而丢失核球的暖色层次。`1 - exp(-x)` 保证无论输入多大，输出都严格小于 1，且在小值区近似线性。

**颜色混合**：

```js
var mixArm  = clamp01(armMask * 1.15);
var mixCore = clamp01(bulge * 1.30 + Math.max(0, 0.26 - t) * 2.6);
var cr = lerp(lerp(0.44, 0.66, mixArm), 1.00, mixCore);
var cg = lerp(lerp(0.56, 0.82, mixArm), 0.79, mixCore);
var cb = lerp(lerp(0.94, 1.00, mixArm), 0.44, mixCore);
```

即：底色偏蓝紫 `(0.44,0.56,0.94)`，旋臂提亮并转向青白 `(0.66,0.82,1.00)`，核心转向暖金 `(1.00,0.79,0.44)`。三层用两次 `lerp` 串起来，顺序不能颠倒：先「底色 → 旋臂」，再「结果 → 核心」。

**Alpha 通道**：存 `e` 的 8 位量化值。纹理用 `LINEAR_MIPMAP_LINEAR` + 各向异性 16，混合模式 `ONE, ONE`（加法），因此盘面是**发光叠加**在星空背景上的，不是覆盖。

### 5.4 粒子的四个族群

`particles = 340000`，按 `Math.random()` 的四个区间分配：

| 族群 | 占比 | 空间分布 | 颜色 | 尺寸 |
|---|---|---|---|---|
| 核球 | 22% | 扁椭球，X 拉长 1.34、Z 压 0.92、Y 压 0.50 | 米白到暖金，10% 偏红 | 0.26–1.76，2% 再 ×2.2 |
| 旋臂 | 52% | 对数螺旋 + 高斯抖动 σ=0.110 | 青白到淡蓝，3.2% 粉（电离氢）、2.4% 青（反射星云）、1.2% 靛紫 | 0.20–2.60，3% 蓝巨星 ×3.4 |
| 银盘 | 19% | 均匀盘 + 螺旋相位调制 | 暗青白，亮度 0.22–1.00 | 0.18–1.03 |
| 银晕 | 7% | 球状晕，半径延伸到 1.14R | 极暗的暖灰 | 0.22–0.92 |

**核球必须单颗很暗**：22% 的粒子挤在很小的体积里，如果单颗足够亮，叠加后就是一团死白的球。这里所有核球粒子的尺寸都被刻意压在 2 像素以下，亮度由密度堆出来。

**旋臂的团块调制**：

```js
var lump = 0.60 + 0.40 *
  (0.5 + 0.5 * Math.sin(theta * 6.0 + Math.sin(theta * 2.3) * 1.7 + arm * 1.9));
```

它让旋臂呈现「一串亮团 + 中间变暗」的节奏，模拟恒星形成区沿旋臂的分布。周期 6.0 意味着每条臂上有约 6 个亮团。

**银盘的臂间暗带**：银盘粒子的亮度不取常数，而由同一个 `armMask` 调制：

```js
var lum = 0.22 + 0.78 * Math.pow(Math.max(0, Math.cos(diff * arms)), 2.2);
```

这一步非常关键：它让「臂之间」自然变暗，而不是靠额外画黑色物质。真实星系照片里的暗带，一半来自尘埃吸收，一半来自「臂间本来就没什么星」。

### 5.5 粒子着色器的能量补偿

这是整个银河渲染里最容易被忽略、但决定成败的一段。

问题：点精灵的尺寸 `gl_PointSize ∝ 1/depth`。远处粒子缩到 1 像素时，如果它的片元颜色不随尺寸变化，那么**远处会变成均匀的暗底色 + 一片 1 像素白点**，看起来像噪点。

解决：让单粒子的峰值亮度正比于它覆盖的面积（以 2 像素为基准）：

```glsl
float s = aSize * uPixelRatio * (uAtten / depth);   // uAtten = 6000
gl_PointSize = clamp(s, 1.0, 56.0);
vEnergy = clamp(s * s * 0.25, 0.09, 1.0);
vEnergy *= smoothstep(90.0, 620.0, depth);          // 贴脸的粒子淡出
```

- `s*s*0.25`：面积正比，除以 4 使 `s=2` 时能量为 1；
- 下限 0.09：防止远处完全消失，保留一层底噪；
- 上限 1.0：防止近处超级亮；
- `smoothstep(90, 620, depth)`：相机推进到星系内部时，最近的粒子会涨成几十像素的白斑。**用深度淡出而不是缩小点尺寸**，因为后者会把远处细尘一起抹平。

片元着色器用指数衰减代替硬边圆盘：

```glsl
float d2 = dot(p, p) * 4.0;
if (d2 > 1.0) discard;
float a = exp(-d2 * 3.4) * (1.0 - d2);
float tw = 0.80 + 0.20 * sin(uTime * 1.7 + vSeed * 43.0);
gl_FragColor = vec4(vColor, a * tw * vEnergy * uOpacity);
```

`exp(-d2*3.4)` 让边缘柔和，`(1-d2)` 保证边界处严格归零，两者相乘得到一个没有硬边的「光斑」。闪烁项 `tw` 幅度只有 ±20%，再大就会像霓虹灯。

### 5.6 暗尘带：只做减法

`dust = 64000` 颗粒子，混合模式为**反向减法**：

```js
gl.blendEquation(gl.FUNC_REVERSE_SUBTRACT);
gl.blendFunc(gl.ONE, gl.ONE);
```

即 `结果 = 已绘制 − 本粒子`。这模拟的是「尘埃挡住了后面的星光」。

**红化**：减去的颜色不是等量的，而是多减蓝、少减红。因为蓝光更容易被星际尘埃散射掉，这就是天文学上的「星际红化」。实现上给尘粒子的颜色通道乘不同系数（R 最少、B 最多），减法自然带来红化。

**丝状走向**：

```js
var wob = Math.sin(r * 0.0105 + arm * 1.7) * 0.055 +
          Math.sin(r * 0.0312 + arm * 0.9) * 0.022;
var theta = logSpiral(r) + phase - 0.115 + wob + gauss() * 0.042;
```

两个不同频率的正弦叠加，让尘带看起来是「被扯开的纤维」而不是一条几何曲线。相位偏移 `-0.115` 让它落在旋臂内侧。

**绘制顺序**：必须先画完所有发光粒子，再画暗尘带。顺序颠倒会导致尘埃吸收不到任何东西，只在黑色背景上画出灰色的点。

### 5.7 远景星空

`bgStars = 12000`，分布在半径 11000–20000 的球壳上。它们**不参与星系自转**（使用单位模型矩阵），因为「恒星不动、星系在转」是我们在银河内部看夜空时的真实体验。

尺寸用固定像素 `uFixedSize`，能量恒为 1，不做距离衰减——它们本来就该是无穷远的点。

### 5.8 球状星团与核心光晕

- `CLUSTER_SPECS`：沿旋臂随机放置约 40 个团块，每个记录半径、亮度、色温；
- 绘制时用公告板（billboard）：把四边形贴在相机空间的 XY 平面上，中心点在 `mv` 中固定，只偏移 `aQuad * uSize`。这样无论怎么转视角，光晕始终正对相机；
- 片元用双指数叠加：`core = (1-d)^3.2`、`halo = (1-d)^1.15 * 0.35`。核心锐利、外围绵软；
- 核心区另有一组常驻光晕 `GLOWS`，带 `0.55 + 0.45*sin(time*2.2)` 的呼吸，幅度不超过 45%。

### 5.9 太阳系标记

太阳在银河系中的真实位置：距离银心约 2.6 万光年，位于猎户臂（本地臂）内侧。本项目把它放在 `sunDist = 1300`（约 0.52R）、方位角 `sunAngle = 2.30`、离盘面高度 `sunY = 22`。

标记由三部分组成：

1. 一个小的暖白色公告板光晕；
2. 一圈脉冲环（`0.7 + 0.3*sin(simTime*3.0)`）；
3. 一行标签「太阳系位置」。

它的世界坐标**每帧重新计算**，因为星系在自转：

```js
var c = Math.cos(galaxySpin), s = Math.sin(galaxySpin);
SUN_MARKER_WORLD[0] = lx * c + lz * s;
SUN_MARKER_WORLD[2] = -lx * s + lz * c;
SUN_MARKER_WORLD[1] = SUN_MARKER_LOCAL[1];
```

拾取与标签都读这份世界坐标，**不允许**在别处重复计算旋转（两处不一致会导致「光标在那、点不到」的经典 bug）。

### 5.10 银河自转

`galaxySpin += dt * (2π / spinPeriod) * timeScale`，`spinPeriod = 180` 秒。

自转在 `1×` 下是「几乎察觉不到但确实在动」的速度，这是刻意选的：太快像洗衣机，太慢则用户以为页面卡住了。`100×` 下大约 1.8 秒一圈，此时能明显看到差速旋转的错觉（实际上这里是刚体旋转，但旋臂的视觉结构会让它看起来像差速）。

### 5.11 银河层的视觉验收

在 1440×810 下，默认视角（`phi ≈ 63.4°`、`theta = π/2`、`r = 3600`）：

1. 能一眼数出**四条旋臂**，且它们从核心向外顺时针或逆时针一致地卷曲；
2. 核心是**暖白色**且明显比旋臂亮，但核心中心不能是纯白死区；
3. 旋臂之间有**可辨认的暗带**，暗带边缘是被「侵蚀」出来的，不是一条等宽的灰线；
4. 放大到 `r = 800` 时，纹理的平滑过渡开始让位于**粒子颗粒**，两者不打架；
5. 缩小到 `r = 7000` 时，整个星系仍能完整出现在画面内，边缘不出现硬切。

## 第 6 章　太阳系层的生成

### 6.1 尺度压缩：为什么必须「作弊」

真实的太阳系尺度无法直接可视化：

- 地球到太阳 1 AU，海王星到太阳 30 AU，比值 30；
- 太阳直径约 0.0093 AU，地球直径约 0.000085 AU；
- 如果按真实比例，在能看见海王星的画面里，地球会小于一个像素。

因此必须做两次非线性压缩，且**必须在代码里显式写清楚这是压缩**，不能假装它是真实比例：

```js
orbitR = 30 * Math.pow(au, 0.55);          // 轨道半径
bodyR  = 1.9 * Math.pow(d / 12742, 0.38);  // 行星半径，d 以公里计
```

代入几个值验证：

| 天体 | AU | 压缩后轨道 R | 直径 km | 压缩后半径 |
|---|---|---|---|---|
| 水星 | 0.387 | 30·0.588 = 17.6 | 4879 | 1.9·0.672 = 1.28 |
| 地球 | 1.000 | 30.0 | 12742 | 1.90 |
| 木星 | 5.204 | 30·2.535 = 76.1 | 139820 | 1.9·3.40 = 6.46 |
| 海王星 | 30.07 | 30·6.62 = 198.6 | 49244 | 1.9·2.13 = 4.05 |

太阳半径取 `5.0`，而不是按同样的公式（按公式会得到 4.9×10⁴，荒谬）。这个 5.0 是刻意压小的：如果取 8，水星轨道（17.6）会几乎贴着太阳表面，视觉上「水星在太阳里」。

**宣传口径**：在 README 与界面里必须写明「轨道与大小为便于观察做了非线性压缩，天体之间的相对顺序与相对大小分级是准确的，但距离不是等比」。

### 6.2 视觉半径与真实半径分离

`mesh.radius` 用于绘制；`spec.diameter` 用于面板展示。**两者之间没有换算关系**，不要试图在代码里从 `mesh.radius` 反推真实直径。

聚焦某颗行星时，相机距离按**视觉半径**计算：

```js
var dist = body.mesh.radius * 6.5 + 4;
```

`+4` 是补偿项：小行星（水星视觉半径 1.28）如果只按 6.5×1.28 = 8.3，相机会贴得太近，边缘畸变严重；加 4 之后，小行星与大行星的「观看距离感」更接近。

### 6.3 行星纹理（`makePlanetPixels`）

**分辨率**：地球 `1024 × 512`，其余 `512 × 256`。地球加倍是因为它是用户最可能停下来细看的目标，海岸线在 512 下会糊成一团。生成耗时：地球约 400ms，其余每颗约 60ms，整体约 1.2 秒，分批让出主线程。

**三类模板**：

**A. 地球型（`spec.earth === true`）**

1. 大陆场：`cont = fbm(u*5.2, v*5.2, seed, 5)`，低频决定大陆位置；
2. 细节场：`detail = fbm(u*16, v*16, seed+91, 3)`，高频给海岸线毛刺；
3. 混合：`elev = cont*0.82 + detail*0.18`；
4. 海陆分界：`0.545`。高于此值为陆地，低于为海；
5. 深海到浅海：`deep = clamp01((0.545 - elev) * 3.4)`，颜色从 `(0.085,0.245,0.470)` 过渡到 `(0.130,0.400,0.560)`；
6. 低地与干燥区：`dry = fbm(u*9, v*9, seed+13, 3)` 决定绿 → 黄褐；
7. 高地/山地：`alt = clamp01((elev - 0.545) * 3.2)`，颜色向灰褐过渡；
8. **极冠**：`capAmt = clamp01((|v-0.5|*2 - 0.80) / 0.14)`，乘以 `capNoise` 后与地表混合，边缘必须是不规则的，不能是「上下两条白边」；
9. **云层**：`cloud = fbm(u*11, v*7, seed+211, 4)`，`clamp01((cloud - 0.52)*3.0) * 0.42` 与地表混合。云量再大就会把大陆糊住；
10. 细粒：`(valueNoise(u*180, v*180, seed+7) - 0.5) * 0.045`，防止出现「塑料感」的纯色块。

**B. 气态巨行星型（`spec.bands > 0`）**

1. 纬向条带：`bandCoord = v * spec.bands + turb*0.55 + fine*0.18`，`stripe = sin(bandCoord*π)*0.5+0.5`；
2. 湍流：`turb = fbm(u*6.4, v*4.2, seed, 4)`，让条带被拉扯成波浪；
3. 颜色在 `band` 与 `color` 之间按 `stripe` 插值；
4. **极区压暗**：`polar = clamp01((|v-0.5|*2 - 0.62) / 0.38)`，向深色过渡；
5. **大红斑**（`spec.spot === true`）：以 `u=0.63, v=0.615` 为中心的椭圆，`dist = sqrt(dx²*3.4 + dy²)/0.085`，`spotAmt = clamp01(1-dist)*0.92`，内部用 `0.86 + 0.14*sin(dist*11)` 做环状涡旋。**必须处理经度环绕**：`dx > 0.5` 减 1、`dx < -0.5` 加 1，否则纹理接缝处会出现半个红斑。

**C. 岩石行星型（其余）**

1. `turb` 与 `fine` 叠加出斑驳表面；
2. 颜色在 `band` 与 `color` 之间按噪声起伏插值；
3. 可选的极冠与细粒。

### 6.4 太阳纹理

`512 × 256`。基础亮度 `0.88`，叠加四层噪声 `n`，再到 `+g2*0.06` 的二次噪声，形成「米粒组织」的观感。太阳是**自发光**天体（`emissive = true`），着色器里跳过兰伯特光照，直接输出贴图颜色。

不允许给太阳画「日冕火焰」——在球体贴图上画不出正确的立体感，只会变成贴纸上的一圈橙边。日冕由公告板光晕负责（见 8.9）。

### 6.5 球体几何

`buildSphere(lonSeg, latSeg) = buildSphere(48, 32)`：约 1600 个三角形。

- 经度分段 48、纬度分段 32 是画质与内存的平衡点；
- 顶点法线直接用归一化位置（球体），不需要额外计算；
- UV：`u = i / lonSeg`、`v = j / latSeg`，`v=0` 为北极；
- 索引按两个三角形一组，注意**绕序**（逆时针为正面），否则背面剔除会把球画成空壳。

### 6.6 光环

土星：内径 `1.36 × 视觉半径`，外径 `2.32 × 视觉半径`，160 段。天王星：`1.70–1.88`，128 段，透明度 0.30。

环的顶点属性包含径向参数 `r ∈ [0,1]`，片元着色器用它做**径向条纹**：

```glsl
float band = 0.55 + 0.45 * sin(r * 42.0 + ...);
```

条纹频率 42 意味着横跨整个环大约有 6–7 条主要明暗带。透明度在内外边缘用 `smoothstep` 淡出，避免出现「圆盘切边」。

环与行星本体的**遮挡关系**需要用深度测试处理：环必须写深度但可以半透明，绘制顺序为「行星 → 环」，且环不关闭深度测试，只关闭背面剔除（环是双面的）。

### 6.7 轨道线

`buildOrbitLine(radius, 256, tiltX)` 生成 257 个点的 `LINE_STRIP`。

- 每个点的 Y 由 `sin(angle) * sin(tiltX)` 给出，即整条轨道绕 X 轴倾斜 `tiltX`；
- 颜色：暗青 `rgba(90,150,200,α)`，α 在银河层为 0、太阳系层为 1；
- 当前聚焦行星的轨道线**高亮**（更亮、更粗），其余保持 0.28 的透明度；
- 轨道线不用深度测试关闭，但要用 `depthMask(false)`，防止它挡住后面的行星。

### 6.8 光照模型

行星片元着色器（`BODY_FS`）的核心三行：

```glsl
float diff = max(dot(N, L), 0.0);
float rim  = pow(1.0 - max(dot(N, V), 0.0), 3.0) * 0.16;
vec3  H    = normalize(L + V);
float spec = pow(max(dot(N, H), 0.0), 28.0) * 0.22;
vec3  col  = base * (0.155 + diff * 1.10) + base * rim + vec3(spec);
```

- **环境项 0.155**：夜面不是纯黑，否则球体边缘会「消失」在背景里；但也不能太高，否则失去「半球受光」的体积感；
- **漫反射 1.10**：略高于 1，让受光面比贴图原色更亮一点；
- **边缘光 `rim`**：指数 3.0、强度 0.16，模拟大气/冰壳的散射。这是让行星「像球」而不是「像圆片」的关键；
- **高光 `spec`**：指数 28、强度 0.22。近景时朝向光源的一小块会明显更亮，这是本次画质提升新增的项；
- **光源方向**固定为从太阳指向行星（太阳在原点）。

不允许加入「平行光 + 点光源 + 补光」三件套。太阳系只有一个光源，多余的补光会让夜面出现不符合物理的亮部，破坏「这是被太阳照亮的球」的直觉。

### 6.9 自转与倾角

- 自转速度用**视觉周期**而非真实周期：
  ```js
  PLANET_SPIN_SECONDS = { mercury:2.6, venus:2.2, earth:1.6, mars:1.8,
                          jupiter:1.1, saturn:1.2, uranus:2.0, neptune:1.5 };
  ```
  如果按真实周期（金星 5832 小时、木星 9.93 小时），在同一个画面里金星几乎不动、木星转成风扇，无法同时观察。
- **逆行**：`retro: true` 的天体（金星、天王星）自转角速度取负；
- **倾角**：`tilt` 为真实轴倾角（度），模型矩阵先绕 Z 轴倾斜，再绕 Y 轴自转。矩阵顺序必须是 `rotateY(spin) · rotateZ(tilt)`，反过来会让自转轴跟着转，看起来像「球在翻滚」；
- **轨道倾角**：`orbitTilt` 用弧度，量级 0.014–0.043，只是让轨道线不完全共面，增加一点真实感，不做精确的黄道倾角换算。

### 6.10 天体数据表字段规范

```js
{
  id: 'earth',            // 唯一标识，用于拾取、聚焦、深链接
  zh: '地球', en: 'Earth',
  diameter: 12742,        // 公里
  orbitDays: 365.26,      // 日
  rotationHours: 23.93,   // 小时
  au: 1.000, moons: 1,
  color: '#2E6BC4', band: '#1B4FA0',
  seed: 37, bands: 0, tilt: 23.44, orbitTilt: 0,
  earth: true,            // 模板选择
  desc: '……',             // 一到两句话的物理描述

```

规则：

1. **`id` 一旦发布不允许改**（深链接与收藏依赖它）；
2. `moons` 必须与当前公认数据一致，或写「已确认」并注明截止版本（木星 95、土星 146、天王星 28、海王星 16）；

5. 所有文本使用中文全角标点，数字与英文之间不加空格以外，不做特殊排版。

### 6.11 数据准确性红线

以下都是**必须**准确的，因为它们会被用户当场核对：

- 八大行星的排列顺序；
- 地球直径 12742 公里、公转 365.26 天；
- 木星是最大的行星，土星有最显著的环；
- 金星与天王星自转方向与多数行星相反；
- 海王星是「先算出来、后看到」的行星。

以下**允许**近似，但必须在文档中声明：

- 轨道半径与行星大小的可视化比例（见 6.1）；
- 自转的视觉速度（见 6.9）；
- 卫星数量（截止日期已注明）。

## 第 7 章　相机与交互

### 7.1 相机模型

相机不是自由飞行的（没有位置 + 四元数），而是**轨道相机**：

```js
var cam = {
  theta, phi, radius,        // 当前值（阻尼后）
  tTheta, tPhi, tRadius,     // 目标值（输入直接改这个）
  target: [x,y,z],           // 注视点
  tTarget: [x,y,z],
  eye: [x,y,z],
  minR, maxR,
  enabled: true
};
```

固定使用球坐标有三个好处：

1. 永远不会「翻转」——`phi` 被夹在 `[0.08, π-0.08]`，北极与南极各有约 4.6° 的死区，避免极点处的万向节奇点；
2. 缩放天然是「朝注视点推近」，不需要射线求交；
3. 平移与旋转解耦：旋转改 `theta/phi`，平移改 `target`，两者互不干扰。

代价是：不能做「第一人称穿行」。这是可接受的取舍——本项目要的是「观察」，不是「漫游」。

### 7.2 `computeEye`

```js
var sp = Math.sin(cam.phi), cp = Math.cos(cam.phi);
cam.eye[0] = cam.target[0] + cam.radius * sp * Math.cos(cam.theta);
cam.eye[1] = cam.target[1] + cam.radius * cp;
cam.eye[2] = cam.target[2] + cam.radius * sp * Math.sin(cam.theta);
```

`phi` 从 +Y 轴量起：`phi = 0` 是正上方俯视，`phi = π/2` 是水平侧视。

默认银河视角 `phi = 1.107`（约 63.4°），这是**观察旋涡结构的标准角度**——再俯视一点，旋臂卷曲会看不出来；再平视一点，盘面会变成一条线。

### 7.3 三种操作的职责划分

| 操作 | 输入 | 改变 | 说明 |
|---|---|---|---|
| 绕转 | 左键拖拽 / 单指拖动 | `theta`、`phi` | 最常用，默认行为 |
| 平移 | 右键 / 中键 / Shift+左键 / 双指整体拖动 | `target` | 用户明确要求「能 x/y 拖动」 |
| 缩放 | 滚轮 / 双指捏合 / `+` `-` 键 | `radius` | 指数曲线 |

**为什么平移要单独指定修饰键**：如果左键既是绕转又是平移，用户无法在按下之前知道会发生什么。把平移交给右键与 Shift，是为了让「默认操作」保持单一。同时在界面上用一行小字提示「Shift 拖动 / 右键拖动可平移」——隐藏功能等于不存在。

### 7.4 平移的像素→世界换算

```js
function panCamera(dx, dy) {
  camBasis();
  var k = 2 * Math.tan(CFG.camera.fov * 0.5) * cam.radius / Math.max(1, screenH);
  var r = camBasis._r, u = camBasis._u;
  for (var i = 0; i < 3; i++) {
    var d = -r[i] * dx * k + u[i] * dy * k;
    cam.tTarget[i] += d;
  }
  clampTarget();
  computeEye();
}
```

推导：屏幕高度 `screenH` 像素对应视锥在距离 `radius` 处的高度 `2·radius·tan(fov/2)`，所以 1 像素 = 该高度除以 `screenH`。乘以鼠标位移就是世界位移。

符号：向右拖动 `dx > 0`，相机应向左移动，场景看起来向右走，所以取 `-r`；向下拖动 `dy > 0`，相机应向上移动，取 `+u`（屏幕 y 向下，与数学 y 向上相反，两者正好抵消）。

**平移边界**：`clampTarget()` 把 `target` 在 XZ 平面上的半径夹到 `panLimit.galaxy = 2300`（银河层）或 `panLimit.solar = 240`（太阳系层）。没有边界的话，用户可以把自己「推离」星系，然后在空白里迷路。

### 7.5 缩放曲线

```js
cam.tRadius = clamp(cam.tRadius * Math.exp(delta * 0.0014), cam.minR, cam.maxR);
```

用指数而不是加法：指数缩放意味着「每一格滚轮改变的倍率相同」，在 3600 与 36 两个尺度上手感一致。加法缩放在远处太慢、在近处太快。

`deltaMode === 1`（行模式）时乘 16 归一化，避免某些浏览器一格滚轮只挪一点点。

### 7.6 拾取

拾取分两条完全不同的路径：

**A. 已知天体的屏幕投影拾取**

`updatePickables(viewMat, projMat)` 每帧把太阳系标记与所有行星投影到屏幕：

```js
{sx, sy, sr, depth, id, visible}
```

`sr` 是投影后的屏幕半径，用于判断点击**球体本身**是否命中；`pickAt(px, py)` 遍历所有可选对象，取「距离/半径」最小者，并给一个 `hitR = max(sr, 20)` 的最小热区——否则水星在远景下只有几个像素，用户根本点不到。

**B. 银盘平面的射线求交**

用于「点空白处朝那里推进」。步骤：

1. 用 `camBasis()` 得到相机的前 `f`、右 `r`、上 `u`；
2. 把屏幕坐标转成 NDC：`nx = px/W*2-1`，`ny = 1-py/H*2`；
3. 方向 `d = f + r·nx·tan(fov/2)·aspect + u·ny·tan(fov/2)`，归一化；
4. 与 `y = 0` 平面求交：`s = -eye.y / d.y`；
5. 若 `s <= 0`（平面在身后）或 `|d.y| < 1e-4`（视线与平面平行）则返回 `null`；
6. 交点半径超过 `1.15R` 则返回 `null`（点到星系外面了）。

这条路径**必须**用真实的相机基向量，不能假设相机的 up 恒为 `(0,1,0)`。当相机俯角很大时，`up` 会切换为 `(0,0,1)`，用固定 up 会让点击位置偏移。

### 7.7 补间

```js
var camTween = { active:false, t:0, dur:0, ease:null, followId:null, from:{}, to:{} };
```

**必须遵守的顺序**：

```js
tweenCam({...}, 900, easeInOutCubic);   // ① 先开补间（内部会清空 camTweenDone）
camTweenDone.push(callback);            // ② 再注册回调
```

`tweenCam()` 的第一行是 `camTweenDone.length = 0`，用于清除上一次未完成的回调。顺序写反会导致回调丢失——这是本项目历史上真实发生过的 bug。

**跟随**：`followId` 非空时，补间结束后相机继续跟随该天体（因为它还在轨道上移动）。跟随在 `updateSolar` 里实现：每帧把 `cam.target` 设为天体世界坐标。

**打断**：新的补间直接覆盖当前补间，不做排队。用户连续点击时，应该「朝最新目标走」，而不是把之前的动画全部播完。

### 7.8 聚焦单颗行星

```js
function focusBody(id) {
  var body = findBodyById(id);
  if (!body) return;
  state = ST.FOCUS;
  focusedId = id;
  var dist = body.mesh.radius * 6.5 + 4;
  var to = tweenToBody(body.worldPos, dist);
  tweenCam(to, CFG.tween.focus, easeInOutCubic, id);
  showInfo(body.spec);
  markActive(id);
}
```

`tweenToBody(worldPos, dist)` 反算球坐标：

```js
var dx = dir[0]/len, dy = dir[1]/len, dz = dir[2]/len;
var phi   = Math.acos(clamp(dy, -1, 1));
var theta = Math.atan2(dz, dx);
```

即「站在天体正上方偏一点的位置看它」。`theta` 保留当前值更好——直接取 `atan2` 会让相机每次都从同一个方向飞来，显得机械。**优先策略**：若当前 `theta` 与目标方向夹角小于 90°，沿用当前 `theta`；否则用 `atan2`。

### 7.9 触摸

- **单指**：绕转（与左键一致）；
- **双指**：
  - 两指距离变化 → 缩放。比例 `pinch.dist / d` 直接乘到 `radius`，不用指数，因为手指间距变化本身就是比例量；
  - 两指中点位移 → 平移。阈值 0.5 像素，避免抖动；
- 双指开始时必须 `drag.active = false`，否则第一根手指的拖拽会和捏合打架；
- 移动端 `touchmove` 需要 `preventDefault()`（`passive: false`），否则页面会跟着滚动。

### 7.10 键盘（P1 新增）

| 按键 | 行为 |
|---|---|
| `←` `→` | 向左/右平移（屏幕空间） |
| `↑` `↓` | 向上/下平移 |
| `+` / `=` | 推近（`radius × 0.85`） |
| `-` / `_` | 拉远（`radius × 1.18`） |
| `R` | 复位当前层视角（等同「复位视角」按钮） |
| `Esc` | 聚焦 → 太阳系；太阳系 → 银河；已折叠 UI 时优先展开 |

| `H` | 隐藏/显示全部 UI（演示模式） |

3. 所有快捷键必须有对应的按钮或提示，避免「只有键盘用户才知道」；
4. 快捷键不能与浏览器冲突（不拦截 `Ctrl/Cmd` 组合）。

### 7.11 双击（P1 新增）

- 银河层：双击空白 → 朝该点推进一级（与单击一致，但**步长更大**：`radius × 0.40`）；
- 银河层：双击太阳系标记 → 直接进入太阳系；
- 太阳系层：双击行星 → 聚焦并推近到 `radius = 视觉半径 × 3.2`（比单击的 6.5 倍更近）；
- 太阳系层：双击空白 → 轻微推近（`× 0.80`）。

双击与单击的区分：用 280ms 内的两次 `pointerup` 且位移都小于 8px。**注意**：单击已经会触发推进，双击会因此叠加两次推进。解决方案是单击延迟 280ms 执行——但这会让单击变迟钝。**采用方案**：单击立即执行；双击检测到时，在单击已推进的基础上再补一次推进。这会让双击的最终结果约等于单击的两步，符合直觉，且不牺牲单击的即时性。

### 7.12 深链接（P1 新增）

用 URL hash 表达状态，便于分享与刷新恢复：

| Hash | 含义 |
|---|---|
| 无 / `#galaxy` | 银河全景默认视角 |
| `#solar` | 太阳系总览 |
| `#body/earth` | 进入太阳系并聚焦地球 |
| `#galaxy/r900` | 银河层，相机半径 900 |

规则：

1. 启动时解析一次，**在纹理生成完成之后**执行，否则目标天体还没建好；
2. 状态变化时用 `history.replaceState` 更新 hash，不产生历史记录堆积（除非是用户主动的层切换，此时用 `pushState` 以便浏览器后退键生效）；
3. 非法 id 静默忽略，回落到默认视角，**不弹错误**；
4. hash 变化时（`hashchange`）也要响应，支持手动改地址栏。

### 7.13 截图导出（P1 新增）

需求：用户想保存当前画面做壁纸或讲义插图。

实现要点：

1. WebGL 画布默认在合成后会被清空，`toDataURL()` 可能得到空白。**不开启** `preserveDrawingBuffer`（会带来性能损失），而是设一个标志：
   ```js
   captureNext = true;   // 点击「截图」时置位
   // 在 frame() 内 draw() 之后、同一帧内：
   if (captureNext) { captureNext = false; dumpCanvas(); }
   ```
2. `canvas.toBlob(cb, 'image/png')` 生成下载链接，文件名 `milkyway-YYYYMMDD-HHmmss.png`；
3. DOM 覆盖层（面板、标签）**不会**进入截图，这是预期行为——导出的是「干净的宇宙」，不是「带 UI 的截图」；
4. 若 `toBlob` 不可用，回退 `toDataURL`；
5. 截图按钮放在工具栏，图标用「相机」字形（可用 Unicode `⛶` 或自制 SVG 内联）。

### 7.14 自适应画质（P1 新增）

目标：在集成显卡或高分屏上不卡死。

采样：启动后跳过前 60 帧（纹理生成、着色器编译会污染样本），取接下来 120 帧的平均 `dt`。

```
avgDt > 1/32   → 降到「中」：dpr 上限 1.25，粒子按 0.6 抽样，关闭暗尘带
avgDt > 1/20   → 降到「低」：dpr = 1，粒子按 0.35 抽样，关闭球状星团与远景星空减半
否则            → 「高」：不做任何削减
```

粒子抽样用 `gl.drawArrays(gl.POINTS, 0, Math.floor(count * ratio))`。因为粒子数据是**逐个独立随机**生成的，前缀就是一个均匀随机子集，抽样后分布不变（只是密度下降）。这一点必须在生成代码里保持——如果将来改成按旋臂顺序生成，抽样就会只保留第一条臂。

**降级只降一次**，不做动态回升：来回切换质量会让画面持续抖动，比稳定在较低画质更难受。

### 7.15 交互验收清单

1. 左键拖拽：画面绕目标旋转，松手后惯性？——**不做惯性**，松手即停；
2. Shift+左键拖拽：画面平移，且平移方向跟随鼠标（拖右场景右移）；
3. 右键拖拽：同上，且不弹出浏览器右键菜单；
4. 滚轮：以画面中心为目标缩放，连续滚到底会进入太阳系；
5. 点击空白：朝该点推进，画面中心最终落到点击位置对应的银盘坐标；
6. 点击行星：聚焦，显示信息面板；
7. `Esc`：从聚焦退回总览、从太阳系退回银河，逐级生效；
8. 触摸双指：缩放与平移同时可用；
9. 键盘方向键：平移连续、无跳变；
10. 刷新带 `#body/mars`：直接落在火星特写。

## 第 8 章　状态机与层混合

### 8.1 四状态的定义与依赖

```js
ST.GALAXY  // 'GALAXY_IDLE'  银河层为主，太阳系层 alpha = 0
ST.SOLAR   // 'SOLAR_IDLE'   太阳系层为主，银河层 alpha = 0
ST.TRANS   // 'TRANSITION'   两层同时存在，alpha 正在交叉
ST.FOCUS   // 'PLANET_FOCUS' 太阳系层，相机跟随某颗行星
```

`ST.FOCUS` **不是**独立的渲染模式，它只是 `SOLAR` 的一个子状态（相机锁定到某颗行星 + 面板展开）。渲染代码里所有 `state === ST.SOLAR` 的判断都必须写成 `state === ST.SOLAR || state === ST.FOCUS`，否则聚焦时轨道线、标签会突然消失。

### 8.2 进入太阳系：两条路径

**路径一：`enterSolar()`**——从「点击太阳系标记」进入。

1. `state = ST.TRANS`；
2. `layerTarget = { galaxy: 0, solar: 1 }`；
3. 相机补间到太阳系默认视角（`target = 原点`，`radius = 360`，`phi = 1.03`）；
4. 补间结束回调里 `state = ST.SOLAR`，切换侧栏与按钮可见性。

**路径二：`diveToSolar()`**——从「滚轮推近到 `diveR` 以内」进入。

与路径一的关键差异：**相机不回到默认视角，而是继续朝当前注视点推进**。用户的体感是「我一直往前飞，飞着飞着就进了太阳系」，而不是「我点了一下，镜头跳回去了」。

实现上 `diveToSolar()` 会在补间中途就把层 alpha 开始交叉，形成「银河淡出、太阳系在同一个空间位置淡入」的效果。这就是 1.3 节「不许有黑场」的具体落地方式。

**禁止**：两条路径都能进入 `ST.TRANS`，且都不检查当前状态。必须在入口处判断 `if (state !== ST.GALAXY) return;`，否则补间会互相覆盖，画面卡在中间状态。

### 8.3 返回银河

`returnToGalaxy()`：

1. 若正在 `ST.GALAXY`，直接返回（幂等）；
2. `state = ST.TRANS`；
3. `layerTarget = { galaxy: 1, solar: 0 }`；
4. 相机补间回银河默认视角：`radius = 3600`、`phi = 1.107`、`theta = π/2`、`target = 太阳系标记的世界坐标`（**不是原点**——回去时应该落在猎户臂附近，让用户知道自己从哪来的）；
5. 回调里 `state = ST.GALAXY`、`focusedId = null`、`hideInfo()`、恢复侧栏天体列表为「银河系」模式。

注意第 4 步的 `target`：太阳标记在银河系里会随自转移动，所以在补间开始时就取当前世界坐标，补间结束后不再跟随（否则用户会觉得画面在自己动）。

### 8.4 层 alpha 的阻尼

```js
function updateLayers(dt) {
  var k = 1 - Math.exp(-dt * 3.6);
  layerAlpha.galaxy += (layerTarget.galaxy - layerAlpha.galaxy) * k;
  layerAlpha.solar  += (layerTarget.solar  - layerAlpha.solar)  * k;
}
```

时间常数约 `1/3.6 ≈ 0.28` 秒，95% 收敛需要约 0.83 秒，与 1700ms 的相机补间配合，形成「相机先动、层后换」的错峰感。

`layerAlpha` 不只是透明度，它还参与：

- **标签可见性**：`alpha > 0.06` 才显示该层标签；
- **拾取开关**：`alpha > 0.35` 才把该层对象放进 `pickables`；
- **绘制跳过**：`alpha < 0.005` 时整层 `return`，省掉几十万粒子的 draw call。

三层使用同一个 alpha 值，必须保持同步，否则会出现「能看到但点不到」的窗口期。

### 8.5 渲染顺序

```
1. clear(color, depth)
2. drawBackgroundStars()        不写深度
3. drawGalaxyLayer()            加法混合，不写深度
   ├─ 盘面纹理
   ├─ 银河粒子
   ├─ 暗尘带（反向减法）
   └─ 球状星团 / 核心光晕（公告板）
4. drawSolarLayer()             写深度
   ├─ 轨道线（depthMask false）
   ├─ 太阳（emissive，不写深度？——写，但关闭背面剔除）
   ├─ 行星（深度测试 + 深度写入）
   ├─ 光环（双面、半透明、写深度）
   └─ 高亮环 / 光晕（公告板，不写深度）
```

**混合状态的切换必须成对**：

```js
gl.enable(gl.BLEND); gl.blendFunc(gl.ONE, gl.ONE);          // 银河发光
gl.blendEquation(gl.FUNC_REVERSE_SUBTRACT); gl.blendFunc(gl.ONE, gl.ONE);  // 暗尘
// 用完必须
gl.blendEquation(gl.FUNC_ADD);
gl.blendFunc(gl.SRC_ALPHA, gl.ONE_MINUS_SRC_ALPHA);         // 常规
```

漏掉恢复 `FUNC_ADD` 会让后续所有半透明绘制（行星、光环、UI 覆盖）变成减法，画面会莫名其妙地变暗或变黑。这是 WebGL 里最常见的一类「状态泄漏」bug。

### 8.6 暂停与时间

- `paused = true` 时 `simTime` 不增长，行星不公转不自转，星系不旋转；
- **相机不受暂停影响**：用户暂停是为了「定住画面看清楚」，不是「冻结交互」；
- `timeScale` 切换立即生效，不补间；
- `simTime` 用于闪烁、脉冲、呼吸等所有周期动效，统一时间源，避免各自动作不同步。

### 8.7 状态机的可测试性

所有状态字符串必须是**全局可见的**（挂在 window 或顶层作用域），以便无头测试读取。测试驻入点在 `updateLabels(viewMat, projMat)` 之后，因为此时投影矩阵与拾取数据都已更新完毕。

推荐的确定性测试方法（本项目已验证）：

```js
function fast() {                       // 强制补间立即收尾
  if (!camTween.active) return;
  camTween.t = camTween.dur;
  updateCamera(0.0001);
}
```

连续调用两次 `fast()` 可以跨过「层切换补间 → 回调里再开一个聚焦补间」的两级链条。**不要依赖 `setTimeout` 或虚拟时间**，无头浏览器的虚拟时间会被启动期的同步重活吃掉。

```
[渐变封面]
```

**防重叠**：候选标签按 `depth` 从近到远排序，依次尝试 7 个偏移位置（`LABEL_OFFSETS = [0,-26,26,-52,52,-78,78]`），与已放置标签做矩形相交测试，全部冲突则隐藏。

**淡出**：`fade = clamp01(1.4 - depth / (银河 6000 / 太阳系 900))`。远处的标签自然变淡，而不是突然消失。

## 第 10 章　性能与启动

### 10.1 启动预算

| 阶段 | 目标耗时 | 实测基线 |
|---|---|---|
| WebGL 初始化 + 着色器编译 | < 120 ms | 约 90 ms |
| 银河粒子/暗尘/背景星 | < 500 ms | 约 420 ms |
| 2048² 盘面纹理（64 批） | < 2600 ms | 约 2290 ms |
| 太阳 + 8 行星纹理 | < 1400 ms | 约 1250 ms |
| **合计到可交互** | **< 4.5 s** | **约 4.0 s** |

超出预算时的处置顺序：先降纹理分辨率（2048 → 1536 → 1024），再降粒子数，**最后**才考虑降行星纹理（那是最影响近景观感的）。

### 10.2 内存预算

| 项 | 大小 |
|---|---|
| 盘面纹理 2048² RGBA + mipmap | 约 21 MB |
| 银河粒子 340k × (3+3+1+1) × 4B | 约 10.9 MB |
| 暗尘 64k | 约 2.0 MB |
| 背景星 12k | 约 0.4 MB |
| 行星纹理 9 张 | 约 4.5 MB |
| 几何缓冲 | 约 1.5 MB |
| **合计** | **约 40 MB** |

移动端上限约 60 MB，超出会被系统回收标签页。任何新增的大缓冲都必须在这个表里登记。

### 10.3 每帧预算（60 fps = 16.7 ms）

| 项 | 目标 |
|---|---|
| 银河粒子 340k 点 | < 6 ms |
| 暗尘 64k 点 | < 1.5 ms |
| 盘面 + 光晕 | < 1 ms |
| 太阳系 9 球 + 环 + 线 | < 2 ms |
| DOM 标签更新 | < 1 ms |
| **合计** | **< 12 ms** |

DOM 标签是最容易被忽略的开销：每个标签每帧写一次 `style.transform` 会触发样式重算。优化手段：只在位移超过 0.5px 时写入。

### 10.4 分片生成

所有超过 100 ms 的同步计算都必须分片：

```js
function buildGalaxyTexture(onDone) {
  var row = 0;
  function step() {
    var end = Math.min(size, row + 32);
    buildGalaxyRows(px, row, end);
    row = end;
    setBootProgress(row / size);
    if (row < size) setTimeout(step, 0);
    else { onDone(px); }
  }
  step();
}
```

`setTimeout(step, 0)` 而不是 `requestAnimationFrame`：后者会被 60fps 节流，64 批需要 1 秒以上；前者在一个事件循环内连续推进，速度更快，同时仍能让出渲染与输入。

### 10.5 首屏策略

加载层不是「遮住白屏的布」，而是一个有信息量的界面：产品名 + 进度条 + 「正在生成 2048×2048 星系纹理」这类具体文案。用户能理解为什么等，等待感会显著降低。

加载层淡出用 `opacity` 过渡 600ms，然后 `display: none`。

### 10.6 自适应画质

见 7.14。补充：自适应只在**首次**启动时判定，之后不再变化；用户手动切换（如果有该选项）则永久生效。

## 第 11 章　降级与可访问性

### 11.1 WebGL 不可用

`fail` 层显示：

```
本页面需要 WebGL 才能显示 3D 星系。
请更换现代浏览器（Chrome / Edge / Firefox / Safari 最新版），
```

**不提供** 2D 回退版本。理由是：一个没有 3D 的「银河系浏览器」没有意义，硬做一个只会误导用户。

### 11.2 上下文丢失

监听 `webglcontextlost` 与 `webglcontextrestored`：

- 丢失时停止渲染循环，显示「图形上下文已丢失，正在恢复」；
- 恢复时**必须重建所有纹理与缓冲**（这是最容易被忽略的一步：WebGL 对象在上下文丢失后全部失效）；
- 重建期间不能接受交互，避免在空上下文上调用 GL 函数。

### 11.3 减少动效

检测 `prefers-reduced-motion: reduce`：

- 关闭粒子闪烁与核心呼吸；
- 补间时长缩短到 300ms；
- 不做缩放/淡入淡出式的层切换，改为瞬切。

### 11.4 对比度

- 正文与面板背景的对比度 ≥ 4.5:1；
- 所有可点击元素有 `:focus-visible` 描边（2px，色 `#7fd4ff`）；
- 不依赖颜色单独传达信息（例如「已选中」除了高亮还要有左侧竖条）。

### 11.5 屏幕阅读器

- 画布有 `role="img"` 与 `aria-label="银河系三维交互视图"`；
- 侧栏列表是 `<ul><li><button>` 结构，可用 Tab 遍历；
- 信息面板打开时，焦点移到面板标题，`Esc` 关闭并把焦点还给触发元素。

## 第 16 章　数学推导详解

本章把前面用到的公式从头推一遍。目的不是炫技，而是**让修改者在改参数之前知道自己在改什么**。所有推导都只用到高中解析几何与一点微积分。

### 16.1 透视投影矩阵

WebGL 的裁剪空间是 `x, y, z ∈ [-w, w]`，深度方向是 `[-w, w]` 映射到 `[0, 1]`（注意与 OpenGL 的 `[-1,1]` 不同，WebGL 的 NDC 深度是 `[-1,1]`，但 `gl_FragDepth` 与深度缓冲是 `[0,1]`，这里的变换要精确）。

本项目手写的 `perspective(fovy, aspect, near, far)` 采用：

```
f = 1 / tan(fovy / 2)

| f/aspect   0     0                       0        |
|    0       f     0                       0        |
|    0       0   (far+near)/(near-far)   2·far·near/(near-far) |
|    0       0    -1                       0        |
```

逐项解释：

- `f` 是「焦距」，`fovy` 是垂直视场角。屏幕高度方向的半宽在单位距离处是 `tan(fovy/2)`，取倒数得到归一化系数；
- 第 0 列除以 `aspect`，因为水平视场角比垂直视场角大（宽屏），需要更大的横向压缩；
- 第 2 行第 2 项 `(far+near)/(near-far)` 与第 2 行第 3 项 `2·far·near/(near-far)`：这两个系数把 `z_view ∈ [-far, -near]` 映射到 `z_ndc ∈ [-1, 1]`。推导方式：设映射为 `z_ndc = (a·z + b) / (-z)`（因为 w 分量为 `-z`），代入两个端点解出 `a`、`b`；
- 第 3 行 `-1`：把视图空间深度取负作为 w，实现透视除法。这也就是为什么 `z` 越远、物体越小。

**为什么 near 不能太小**：深度缓冲的精度在中远距离与 `1/z` 成正比，`far/near` 比值越大，远处精度越差。`far/near = 100000` 时，在距离 1000 处相邻两个深度值的间距大约是 `1000² / (near · 2^24)` 量级，容易出现 z-fighting。本项目通过「近景物体必须靠近相机」来规避（见 4.3），而不是靠放大 near。

### 16.2 视图矩阵与 `lookAt`

`lookAt(eye, center, up)` 的构造：

```
z 轴 = normalize(eye - center)      // 相机看向 -z，所以 z 轴是从目标指向相机
x 轴 = normalize(cross(up, z))
y 轴 = cross(z, x)
```

得到的旋转矩阵把世界坐标转到相机坐标，平移部分为 `-R·eye`。写成列主序 4×4 时，前三列是 `x`、`y`、`z` 轴向量，第四列是 `-R·eye`。

**极点问题**：当 `up` 与 `z` 平行时，`cross(up, z)` 退化为零向量，归一化会得到 `NaN`，整个画面消失。本项目的 `phi` 被夹在 `[0.08, π-0.08]`，理论上不会精确平行；但浮点误差仍可能让 `sin(phi)` 极小，因此额外做了一次「长度过短则退回备用轴」的容错。

**`up` 的切换**：当相机接近正上方或正下方时，继续用 `(0,1,0)` 会让画面绕自身轴快速旋转（因为 up 与视线几乎平行）。切换为 `(0,0,1)` 后，画面保持「北在屏幕上方」的直觉。切换阈值 `0.12` 弧度（约 6.9°）是经验值：太小会在极点附近突然翻转，太大会在正常视角下用错参考轴。

### 16.3 球坐标到直角坐标

```
x = r · sin(φ) · cos(θ)
y = r · cos(φ)
z = r · sin(φ) · sin(θ)
```

`φ` 从 +Y 轴量起，`θ` 在 XZ 平面内从 +X 轴逆时针量起。反解：

```
r = √(x² + y² + z²)
φ = arccos(y / r)
θ = atan2(z, x)
```

`acos` 的定义域必须夹到 `[-1, 1]`，否则浮点误差会让 `y/r` 略大于 1 而返回 `NaN`——这是相机突然消失的最常见原因。

### 16.4 屏幕像素到世界单位的换算

设视场角 `fov`（垂直），相机到目标距离 `r`，屏幕高度 `H` 像素。视锥在距离 `r` 处的垂直高度为：

```
h_world = 2 · r · tan(fov/2)
```

因此 1 像素对应：

```
k = h_world / H = 2 · r · tan(fov/2) / H
```

这就是 `panCamera` 里的 `k`。它只在「注视点所在的平面」上严格成立；对于更近或更远的物体，实际的世界位移会不同。但对于平移操作，用注视点平面做近似是标准的做法，用户感知不到差异。

### 16.5 射线-平面求交

射线：`P(t) = eye + t·d`，`|d| = 1`。
平面：`y = 0`，即法线 `n = (0,1,0)`、过原点。

代入：`eye.y + t·d.y = 0`，解出：

```
t = -eye.y / d.y
```

三个退化条件：

1. `d.y ≈ 0`：射线与平面平行，无交点或无穷多交点；
2. `t <= 0`：交点在相机背后；
3. 交点超出星系半径：点到了「星系外面」。

方向向量 `d` 的构造来自视锥：

```
d = f + r_axis · nx · tan(fov/2) · aspect + u_axis · ny · tan(fov/2)
```

其中 `nx, ny ∈ [-1,1]` 是 NDC 坐标，`f` 是前向量，`r_axis`、`u_axis` 是相机的右、上向量。这个式子成立的前提是 `f` 是单位向量且 `r_axis`、`u_axis` 与之正交——`camBasis()` 保证了这一点。

### 16.6 指数阻尼的物理意义

```js
x += (x_target - x) * (1 - e^{-dt·λ})
```

这是一个一阶低通滤波器的离散形式。连续形式为：

```
dx/dt = λ · (x_target - x)
```

解为 `x(t) = x_target + (x₀ - x_target)·e^{-λt}`。也就是说：**到达目标的比例按指数收敛，与步长无关**。

不同 `λ` 的观感：

| λ | 95% 收敛时间 | 观感 |
|---|---|---|
| 4 | 0.75 s | 拖沓、像有惯性 |
| 11 | 0.27 s | 跟手、有一点点柔化（当前值） |
| 20 | 0.15 s | 几乎没有阻尼，略显生硬 |

层切换用 `λ = 3.6`，因为它需要与 1700ms 的相机补间配合，慢一点更自然。

### 16.7 软饱和

`e = 1 - exp(-L·k)` 的导数 `e' = k·exp(-L·k)` 在 `L = 0` 处等于 `k`，因此**小值区近似线性**；当 `L → ∞` 时 `e → 1`。这正好解决了「几十项叠加后中心过曝」的问题。

它的一个副作用是：整体亮度会被压低（因为同样输入下输出小于线性）。因此在调参时，`k` 通常要比「线性系数」大 30%–50%，这是正常的，不要因此以为调错了。

### 16.8 对数螺旋的弧长

严格计算对数螺旋的弧长需要积分：

```
s = ∫ √(r² + (dr/dθ)²) dθ,  dr/dθ = a·b·e^{bθ} = b·r
  = ∫ r·√(1 + b²) dθ
```

因为 `r = a·e^{bθ}`，所以 `dθ = dr / (b·r)`，代入得：

```
s = ∫ (√(1+b²) / b) dr = (√(1+b²) / b) · (r - r₀)
```

结论：**弧长沿半径线性增长**。这意味着按半径均匀采样螺旋，在弧长上也是均匀的——这正是本项目粒子生成时「先随机取半径，再算方位角」能自然得到均匀臂密度的原因。如果改用「沿曲线等距采样」反而会得到中心过密的错误分布。

### 16.9 粒子尺寸与能量的关系

点精灵在屏幕上覆盖的面积 `A ∝ s²`，其中 `s = gl_PointSize`。若片元颜色固定为 `c`，则单颗粒子的总能量为 `E ∝ c·s²`。为了让总能量与尺寸解耦（即「大粒子比小粒子亮，但单位面积亮度相同」），需要：

```
c ∝ 1 / s²
```

本项目的做法相反：把 `c` 固定，让 `s` 决定尺寸，同时用 `vEnergy = clamp(s²/4, …)` 让**亮度**随尺寸增长。这相当于让粒子表现为「有固定表面亮度的发光体」，而不是「固定总能量的点」。对于星系而言，后者才是对的：亮星本来就比暗星亮得多，不是「同样的能量摊在更大面积上」。

这一段的取舍经常被搞反：如果每个粒子总能量守恒，远处的恒星会集体变暗，星系边缘会「蒸发」；如果亮度恒定，近处的尘埃会糊成一片白。本项目的折中是——亮度随面积增长，但设上下限，再用深度淡出处理贴脸粒子。

### 16.10 屏幕半径的投影

`updatePickables` 中计算行星屏幕半径：

```js
var sr = (worldRadius / dist) * (screenH * 0.5) / Math.tan(fov * 0.5);
```

推导：一个世界半径为 `R` 的球，在距离 `dist` 处，其角半径为 `atan(R/dist) ≈ R/dist`（小角近似）；屏幕上半高对应 `tan(fov/2)` 弧度，因此屏幕半径（像素）为：

```
sr = (R / dist) / tan(fov/2) · (H/2)
```

当 `dist` 接近 `R` 时，小角近似失效，球会占据大半个屏幕，此时 `sr` 会被高估。本项目在实际使用时对 `sr` 做了上下限截断，并且 `pickAt` 使用 `max(sr, 20)` 的热区，因此误差不影响可用性。

## 第 17 章　着色器逐行注释

本项目的着色器全部内联在 JS 字符串数组里，用 `.join('\n')` 拼接。这样做的理由：单文件约束，且避免模板字符串里的反引号与 `$` 冲突。

### 17.1 粒子顶点着色器（`PARTICLE_VS`）

```glsl
attribute vec3  aPos;       // 世界坐标
attribute vec3  aColor;     // 线性 RGB（未做 sRGB 转换）
attribute float aSize;      // 基准尺寸（世界单位尺度）
attribute float aSeed;      // 每颗粒子的随机种子，用于闪烁相位
uniform   mat4  uProj, uView, uModel;
uniform   float uPixelRatio; // 设备像素比
uniform   float uAtten;      // 距离衰减系数，银河 6000，背景星 0
uniform   float uFixedSize;  // >0 时使用固定像素尺寸（远景星空）

varying vec3  vColor;
varying float vSeed, vEnergy;

void main() {
  vColor = aColor;
  vSeed  = aSeed;

  vec4 mv = uView * (uModel * vec4(aPos, 1.0));
  float depth = max(-mv.z, 1.0);          // 相机看向 -z，取负得到正距离

  if (uFixedSize > 0.0) {
    gl_PointSize = uFixedSize * uPixelRatio;
    vEnergy = 1.0;
  } else {
    float s = aSize * uPixelRatio * (uAtten / depth);
    gl_PointSize = clamp(s, 1.0, 56.0);
    vEnergy = clamp(s * s * 0.25, 0.09, 1.0);
    vEnergy *= smoothstep(90.0, 620.0, depth);
  }
  gl_Position = uProj * mv;
}
```

逐行要点：

- `max(-mv.z, 1.0)`：`mv.z` 是负的（相机空间朝前为 -z），取负得到正距离；下限 1.0 防止相机恰好穿过粒子时除零；
- `uModel` 对银河粒子是星系自转矩阵，对背景星是单位矩阵；
- `uPixelRatio` 必须参与点尺寸计算，否则 Retina 屏上的粒子只有一半大小；
- `clamp(s, 1, 56)`：下限 1 是硬件限制（小于 1 无效），上限 56 防止近处粒子撑满屏幕；
- `smoothstep(90, 620, depth)`：相机推进到星系内部时，最近的一批粒子会被淡出，避免「白色大斑块」；
- `vEnergy` 的下限 0.09：保证远处仍有底噪，否则星系边缘会突然「消失」。

### 17.2 粒子片元着色器（`PARTICLE_FS`）

```glsl
precision mediump float;
uniform float uTime, uOpacity;
varying vec3  vColor;
varying float vSeed, vEnergy;

void main() {
  vec2 p  = gl_PointCoord - vec2(0.5);   // [-0.5, 0.5]
  float d2 = dot(p, p) * 4.0;            // 归一化到 [0, 1]
  if (d2 > 1.0) discard;                  // 圆外丢弃
  float a = exp(-d2 * 3.4) * (1.0 - d2);
  float tw = 0.80 + 0.20 * sin(uTime * 1.7 + vSeed * 43.0);
  gl_FragColor = vec4(vColor, a * tw * vEnergy * uOpacity);
}
```

- `mediump` 足够：粒子是小尺寸、低精度需求；
- `gl_PointCoord` 在点精灵内从 `(0,0)` 到 `(1,1)`，减 0.5 后中心为原点；
- `* 4.0` 是因为半径 0.5 时 `dot(p,p) = 0.25`，乘 4 归一到 1；
- `exp(-d2*3.4)` 的高斯型衰减让边缘柔和；
- `(1-d2)` 保证在 `d2 = 1` 处严格为 0，避免 `discard` 边界出现硬切；
- 闪烁幅度 ±20%，频率 1.7 rad/s，相位用 `vSeed * 43.0` 打散（乘 43 是为了让相邻种子相差较大，避免同步闪烁）。

### 17.3 公告板顶点着色器（`BILLBOARD_VS`）

```glsl
attribute vec2 aQuad;   // [-1,1]²
uniform mat4 uProj, uView;
uniform vec3 uCenter;
uniform float uSize;
varying vec2 vUv;

void main() {
  vUv = aQuad;
  vec4 mv = uView * vec4(uCenter, 1.0);
  mv.xy += aQuad * uSize;     // 在相机空间直接偏移，天然正对相机
  gl_Position = uProj * mv;
}
```

关键在 `mv.xy += ...`：在**视图空间**偏移，而不是世界空间。视图空间的 XY 平面就是屏幕平面，因此四边形永远正对相机，不需要每帧重建世界空间顶点。

### 17.4 公告板片元着色器（`BILLBOARD_FS`）

```glsl
float d = length(vUv);
if (d > 1.0) discard;
float core = pow(max(0.0, 1.0 - d), 3.2);
float halo = pow(max(0.0, 1.0 - d), 1.15) * 0.35;
gl_FragColor = vec4(uColor, (core + halo) * uOpacity);
```

- `core` 指数 3.2：核心亮、边缘快速衰减，形成「点光源」；
- `halo` 指数 1.15：近似线性衰减，形成「弥散光晕」；
- 两者相加：中心亮而不死白（因为 `core+halo` 在 `d=0` 处等于 1.35，配合 alpha 混合后会略微过曝，这是想要的效果——中心应该「亮到溢出」）。

### 17.5 盘面纹理着色器

```glsl
// 顶点
attribute vec2 aQuad;
uniform float uExtent;
varying vec2 vUv;
void main() {
  vUv = aQuad * 0.5 + 0.5;
  vec3 lp = vec3(aQuad.x * uExtent, 0.0, aQuad.y * uExtent);
  gl_Position = uProj * uView * (uModel * vec4(lp, 1.0));
}
```

四边形顶点是 `(-1,-1)…(1,1)`，映射到世界坐标 `[-uExtent, uExtent]²` 的 XZ 平面，同时映射到 UV `[0,1]²`。`uExtent = R * 1.06`，与纹理生成的留白系数一致。

```glsl
// 片元
precision highp float;
uniform sampler2D uTex;
uniform float uOpacity;
varying vec2 vUv;
void main() {
  vec4 c = texture2D(uTex, vUv);
  gl_FragColor = vec4(c.rgb * c.a, c.a * uOpacity);
}
```

- `highp` 用于纹理采样：`mediump` 在 2048² 纹理上会产生明显的量化色带；
- 乘 `c.a`：纹理的 alpha 通道存的是亮度包络，用它调制 RGB 可以让星系的边缘柔和地消失，而不是出现方形边界；
- 输出 alpha 也乘 `c.a`，使加法混合的贡献与亮度一致。

### 17.6 行星顶点着色器（`BODY_VS`）

```glsl
attribute vec3 aPos, aNormal;
attribute vec2 aUv;
uniform mat4 uProj, uView, uModel;
uniform mat3 uNormalMat;
uniform vec3 uSunPos;       // 世界空间光源位置（原点）
varying vec2 vUv;
varying vec3 vNormal, vWorldPos;

void main() {
  vec4 wp = uModel * vec4(aPos, 1.0);
  vWorldPos = wp.xyz;
  vNormal   = normalize(uNormalMat * aNormal);
  vUv       = aUv;
  gl_Position = uProj * uView * wp;
}
```

- 法线必须用 `uNormalMat`（左上 3×3 归一化），不能用模型矩阵直接乘——模型矩阵包含缩放，会破坏法线方向；
- `uSunPos` 在顶点着色器里声明但未使用，实际在片元里通过 `vWorldPos` 与固定原点计算。保留它是为了将来支持「多光源」时不需要改接口（但按第 16 章禁止事项，P1 不实现多光源）。

### 17.7 行星片元着色器（`BODY_FS`）

```glsl
precision highp float;
uniform sampler2D uTex;
uniform float uOpacity;
uniform vec3  uSunPos;
uniform float uEmissive;
varying vec2 vUv;
varying vec3 vNormal, vWorldPos;

void main() {
  vec3 base = texture2D(uTex, vUv).rgb;
  vec3 N = normalize(vNormal);
  vec3 L = normalize(uSunPos - vWorldPos);
  vec3 V = normalize(cameraPosition - vWorldPos);   // cameraPosition 为内置
  float diff = max(dot(N, L), 0.0);
  float rim  = pow(1.0 - max(dot(N, V), 0.0), 3.0) * 0.16;
  vec3  H    = normalize(L + V);
  float spec = pow(max(dot(N, H), 0.0), 28.0) * 0.22;
  vec3 col = base * (0.155 + diff * 1.10) + base * rim + vec3(spec);
  col = mix(base, col, 1.0 - uEmissive);   // 太阳：uEmissive=1，直接输出贴图色
  gl_FragColor = vec4(col, uOpacity);
}
```

- `cameraPosition` 是 WebGL 的内置 uniform（视图矩阵的逆），无需手动传入；
- 环境项 0.155 加在 `base` 上，夜面呈现「微光」而不是纯黑；
- `rim` 用 `pow(1 - N·V, 3)`：视线越接近切线方向，值越大，形成边缘光；
- `spec` 用半程向量 `H` 的 28 次方：指数越高高光越小越锐；
- `mix(base, col, 1 - uEmissive)`：太阳（`uEmissive = 1`）直接输出贴图原色，不受光照影响。

### 17.8 光环着色器

顶点属性包含径向参数 `aR ∈ [0,1]`：

```glsl
float band = 0.55 + 0.45 * sin(aR * 42.0 + sin(aR * 9.0) * 2.0);
float edge = smoothstep(0.0, 0.06, aR) * (1.0 - smoothstep(0.92, 1.0, aR));
vec3  col  = mix(uColorB, uColorA, band);
gl_FragColor = vec4(col, uOpacity * edge * (0.35 + 0.65 * band));
```

- `42.0` 控制条纹密度；
- 内层 `sin(aR*9)*2` 让条纹间距不均匀，更像真实的环；
- `edge` 在内外边缘各做一段淡出，避免圆盘状的硬边；
- alpha 也随 `band` 变化，让暗缝真正「透过去」。

### 17.9 轨道线着色器

```glsl
// 顶点
attribute vec3 aPos;
uniform mat4 uProj, uView;
void main() { gl_Position = uProj * uView * vec4(aPos, 1.0); }

// 片元
precision mediump float;
uniform vec4 uColor;
void main() { gl_FragColor = uColor; }
```

简单到不能再简单。轨道线是 1px 宽的 `LINE_STRIP`，无法控制线宽（WebGL 的 `lineWidth` 在多数实现里被限制为 1）。如果要更粗的轨道线，只能改用三角形带（quad strip），P1 不做。

## 第 18 章　调参与审美

本章记录「为什么是这些数字」。这些数字不是随便试出来的，而是每次改动都会重新看三张基准截图后确定的。

### 18.1 亮度层次的三段式

一张「看起来像星系」的图，必须同时有：

1. **大面积的暗**：银盘外围与臂间，亮度接近 0；
2. **中等亮度的结构**：旋臂主体，能看出走向；
3. **极小面积的高亮**：核心、亮星、星团。

如果三者比例失衡，会出现三种典型失败：

| 失败 | 表现 | 原因 | 修法 |
|---|---|---|---|
| 灰蒙蒙 | 整张图像蒙了一层雾 | 暗部太亮（粒子能量下限过高、背景星太多） | 降 `vEnergy` 下限、减背景星 |
| 死白 | 核心是一团纯白 | 缺少软饱和，或核球粒子太大 | 加 `1-exp(-x)`、压核球尺寸 |
| 噪点 | 像电视雪花 | 粒子太亮太密，且没有纹理打底 | 加盘面纹理、降粒子能量 |

本项目的现状是三者平衡后的结果：盘面纹理负责 (2)，粒子负责 (3)，暗尘与臂间调制负责 (1)。

### 18.2 旋臂的「锐度」

`cos(diff·arms)^2.6` 里的指数是旋臂锐度的唯一控制：

- 指数 1.5：四条臂互相渗透，看起来像「两个旋臂的模糊版」；
- 指数 2.6：能数清四条，边缘有毛刺（当前值）；
- 指数 4.0：变成四条细线，中间大片空白，像「画上去的」。

调高指数时，必须同时提高粒子密度，否则细线会显得空洞。

### 18.3 色彩的三层与对比

- 核心暖（R > G > B）、旋臂冷（B > G > R）；
- 暖冷对比不能太强，否则像「贴了两种颜色」；
- 粉红/青色的星云点只占 5% 左右，是「点缀」不是「主色」；
- 暗尘带的减法在暖区更明显（暖色亮度高，减掉后反差大），这是自然形成的层次，不需要额外处理。

### 18.4 行星配色

取「印象色」而非物理反照率：

| 行星 | 基色 | 条带色 | 说明 |
|---|---|---|---|
| 水星 | `#9A8B7E` | `#776A5E` | 灰褐，无大气 |
| 金星 | `#E8C48A` | `#C9A46A` | 暖黄，被云层包裹 |
| 地球 | `#2E6BC4` | `#1B4FA0` | 海蓝，贴图另有大绿与白 |
| 火星 | `#C1613A` | `#8F4527` | 锈红 |
| 木星 | `#C9A87C` | `#A07A4E` | 米褐条纹 |
| 土星 | `#E0C894` | `#C0A26A` | 淡金 |
| 天王星 | `#9FE3E8` | `#7DC8D4` | 青蓝，甲烷吸收红光 |
| 海王星 | `#3D63C9` | `#2C4A9E` | 深蓝 |

如果用真实的平均反照率换算成颜色，金星会变成灰白、海王星会接近黑——这不是用户想看的。科学可视化的原则是：**结构准确、色彩可读**。

### 18.5 相机角度的选择

- 银河默认 `phi = 63.4°`：这个角度下，旋臂的「S」形最明显，同时盘面还有足够的厚度感；
- 太阳系默认 `phi = 58.9°`：稍微俯视，能看到轨道线是椭圆而不是直线；
- 聚焦行星时相机停在「行星正上方偏 30°」的位置：完全正上方会让自转看不出来，完全侧面会让球变成圆。

### 18.6 补间时长

- 900ms：点击推进。再快会「闪现」，再慢会「拖沓」；
- 1200ms：聚焦行星。距离更远，需要更长时间；
- 1700ms：层切换。这是「换世界」级别的动作，需要仪式感；
- 300ms：UI 面板滑入。UI 属于「界面反馈」，必须比相机快，否则用户会觉得界面「粘手」。

### 18.7 常见审美问题与对策

**问题：旋臂看起来像「画上去的曲线」**
对策：加大噪声扰动（`(n1-0.5)*2.6`），并在粒子层增加「亮团调制」（`lump`），让臂有断续感。

**问题：核心太圆、太亮**
对策：核球在 X 方向拉长 1.34，做成棒状；降低核心光晕的 alpha；用更暖的色温而不是更高的亮度。

**问题：放大后纹理糊**
对策：2048 纹理 + 各向异性过滤；粒子层在近处接管细节；`vEnergy` 的深度淡出避免大斑块。

**问题：行星像「贴了图的球」**
对策：加边缘光与高光；夜面保留 0.155 的环境光；自转轴倾角必须真实（天王星躺倒）。

**问题：标签乱飞、互相压**
对策：按深度排序 + 7 个候选偏移 + 矩形碰撞检测。

### 18.8 调参流程（必须遵守）

1. 改**一个**参数；
2. 重新生成三张基准截图（银河远景、银河近景、太阳系）；
3. 与上一版对比；
4. 只有三张都变好（或至少不变坏）才保留；
5. 记录本次改动与理由。

禁止「一次改五个参数然后凭感觉说更好看」——这样无法归因，也无法回滚到单点。

## 第 19 章　调试手册

本章是一个「症状 → 定位 → 修复」的对照表。所有条目都来自本项目真实踩过的坑，不是假设。

### 19.1 画面全黑

按可能性从高到低排查：

**第一，着色器编译失败。** 浏览器不会在页面上显示错误，只会静默黑屏。定位方法：在 `gl.compileShader` 之后立刻读 `gl.getShaderParameter(sh, gl.COMPILE_STATUS)`，失败则 `gl.getShaderInfoLog(sh)` 并把它写进调试浮层。本项目所有着色器编译都走 `makeProgram()`，任何一步失败都会 `throw`，错误信息包含着色器名与日志——**不要吞掉这个异常**，它是黑屏的第一现场。

**第二，矩阵全零或含 `NaN`。** 常见于 `lookAt` 的极点退化、`acos` 越界、除以零。定位方法：在每帧开头检查 `viewMat`、`projMat` 的关键元素，发现 `NaN` 就停帧并在浮层里打印 `cam` 状态。修复：给所有除法加分母保护，给 `acos` 加 `clamp(x, -1, 1)`。

**第三，相机在物体内部且朝向错误。** `radius` 小于物体的近平面距离。定位：浮层显示 `cam.radius` 与 `cam.target`。修复：检查缩放下限是否被误改。

**第四，`gl.drawArrays` 的 `count` 为 0。** 粒子数量在自适应画质里被乘成小数，`floor` 后偶尔为 0（只可能发生在极小分辨率极端情况下）。修复：加 `Math.max(1, ...)`。

**第五，canvas 尺寸为 0。** 页面在 `display:none` 的容器里初始化，`clientWidth` 为 0。修复：初始化前检查尺寸，为 0 时延后一帧。

### 19.2 画面发白、像蒙了一层雾

- 检查 `vEnergy` 的下限（当前 0.09）：抬高会整体提亮；
- 检查背景星数量与尺寸：12000 颗、固定 1.5px 是当前值，翻倍会明显发灰；
- 检查加法混合是否被用于非粒子物体：加法混合下每个重叠区域都会累加，UI 材质的环、盘面纹理如果误用加法混合会立刻发白；
- 检查是否忘记恢复混合状态：暗尘用 `FUNC_REVERSE_SUBTRACT`，用完后必须恢复 `FUNC_ADD` 与 `SRC_ALPHA, ONE_MINUS_SRC_ALPHA`。**这是最容易犯的错误**，因为错误不会立刻显现，而是在下一次绘制时把别的物体也减掉。

### 19.3 星系中心出现黑色圆环

这是「核球调参」的经典事故。原因：核球粒子的半径分布在内外边界之间快速下降，而盘面纹理在中心又有一个亮核，两者在边界处不匹配，形成一圈「没有粒子也没有纹理」的暗带。

修复方式（按优先级）：

1. 让核球的半径分布延伸到 0（而不是从某个最小半径开始），重叠覆盖；
2. 让核球边缘的粒子能量随半径平滑衰减，而不是硬截断；
3. 调整盘面纹理的 `bulge` 系数，让它与粒子核球的半径尺度一致（当前都是 `R * 0.175` 量级）。

**不要**试图用提高整体亮度来「填平」暗环——那只会把暗环变成亮环。

### 19.4 暗尘减法把整个画面吃掉

暗尘带使用 `blendEquation(FUNC_REVERSE_SUBTRACT)`，绘制顺序为「先盘面纹理，再暗尘，再粒子」。如果暗尘的绘制范围（四边形大小）大于盘面，减法会把画面背景也减掉，表现为「星系外面有一圈变黑」。

修复：暗尘四边形的 `extent` 必须与盘面一致；并且暗尘纹理的 alpha 在边缘要归零。

另一个坑：如果暗尘绘制后没有恢复 `FUNC_ADD`，下一帧的粒子会继续使用减法，整个星系会逐帧变暗直到全黑。**症状是「画面慢慢变黑」**，看到这个现象第一件事就是查混合状态。

### 19.5 点击没反应

`pickAt` 返回 `null` 的三种情况：

1. **射线打空**：焦点不在任何可拾取物上。验证方法：在拾取后把 `ray` 的 `t`、`hit` 打印出来；
2. **热区太小**：行星在屏幕上只有 3px，`max(sr, 20)` 的 20px 热区也可能因为点击位置偏差而错过。修复：把热区下限提到 26px，或改用「离屏幕距离最近且在 40px 内」的规则；
3. **`pickables` 没更新**：`updatePickables` 只在相机变化或状态切换时调用，如果行星在自转但相机没动，屏幕坐标仍是旧值。当前的实现每帧调用，代价很小。

**注意**：`pointerup` 与 `pointerdown` 之间的移动距离超过阈值时必须取消点击（当前 5px）。否则拖动结束时会误触发一次「点击放大」，这是最容易被用户投诉的手感问题。

### 19.6 拖动方向与预期相反

不是 bug，是坐标系约定。检查：

- 水平拖动：`tTheta -= dx * 0.0042`。`theta` 增加是绕 +Y 轴逆时针，所以「向右拖 → theta 减小 → 场景顺时针转 → 物体向右移动」。如果用户期望「抓取式」拖动（拖动方向即物体移动方向），符号就是对的；
- 垂直拖动：`tPhi -= dy * 0.0042`。向下拖 `dy > 0` → `phi` 减小 → 相机升高 → 看到更多顶部。这也是「抓取式」。

如果改成「相机式」（拖动方向即相机绕行方向），两个符号都要翻转。**不要只翻一个**。

### 19.7 平移时画面抖动

原因通常是「平移量按帧计算」而不是「按时间计算」。每帧的 `dt` 不同，帧率不稳时位移量忽大忽小。当前平移只在拖动的 `pointermove` 事件里用像素增量换算，天然按事件触发，不存在抖动；但如果改成「按住方向键连续平移」，必须乘 `dt`。

另一个来源：`tTarget` 与 `target` 同时被写，阻尼跟着抖。规则是：**输入只写 `t*` 目标值，阻尼只写当前值**。

### 19.8 补间「飞过去又弹回来」

`tweenCam` 开头清空回调数组，结尾设置 `active`。如果调用者在 `tweenCam()` **之前** push 回调，回调会被清掉——表现为「补间结束后什么都没发生」。如果调用者在补间进行中再次调用 `tweenCam`，上一个补间的回调同样会被丢弃。

正确的顺序永远是：

```js
tweenCam(to, dur, ease, followId);
camTweenDone.push(function () { /* 后续动作 */ });
```

### 19.9 层切换时闪黑

原因：层 alpha 用阻尼过渡，但**相机的补间与层 alpha 的阻尼不是同一时间常数**。如果相机到位了而 alpha 还没到位，会出现「新层已经清楚、旧层还没消失」的双重曝光；反之则出现「旧层没了、新层还没来」的黑场。

修复：让 alpha 的阻尼系数与补间时长的关系固定下来。当前 `λ = 3.6` 对应 95% 收敛约 0.83 秒，而补间是 1.7 秒——这在数学上不同步，但视觉上可接受，因为 alpha 在 0.5 秒左右就已经「看不出区别」了。如果要更严格，可以把 alpha 直接绑定到补间的进度 `t/dur`，用缓动函数驱动。

### 19.10 无头浏览器截图是空白

这是本项目调试中最耗时的问题，记录完整结论：

- `--headless=new --disable-gpu` 下，WebGL 走 SwiftShader 软件渲染，能出图，但**极慢**；
- `--virtual-time-budget=N` 会快进定时器，但**启动期的同步重活（纹理生成约 2.3 秒）会吃掉整个预算**，导致截图落在第 1–3 帧，画面还是黑色的（星系粒子需要几帧才累积到稳定亮度）；
- `requestAnimationFrame` 在虚拟时间下会被节流，`dt` 的计算依赖 `performance.now()`，虚拟时间推进与真实渲染不同步。

**正确的调试方式**：注入一个「强制推进」的探针，在固定帧号执行确定性的状态操作（而不是寄希望于时间流逝）：

```js
function fast() {
  if (!camTween.active) return;
  camTween.t = camTween.dur;   // 直接把进度推到终点
  updateCamera(0.0001);         // 用一个极小的 dt 触发一次结算
}
```

同时在页面左上角挂一个 `position:fixed` 的调试浮层，每帧更新 `textContent`。因为无头模式下拿不到 `console` 输出，**浮层是唯一可靠的观察窗口**。截图后用眼睛读浮层上的文字即可。

### 19.11 纹理生成卡住主线程

纹理是 2048×2048，逐像素计算 fBm，纯 JS 大约需要 2.3 秒。当前的实现是「每 32 行一批，`setTimeout(step, 0)`」。如果发现页面在生成期间完全无响应，检查：

- 是否在批之间做了 `await new Promise(r => setTimeout(r, 0))` 而不是同步循环；
- 批大小是否过大（32 行 × 2048 像素 = 65536 次 fBm 调用，约 15ms，接近一帧）；
- 是否在生成期间还触发了布局（比如频繁修改 DOM 文本）。

**不要在纹理生成路径里调用 `Math.random()`**：它会让每次刷新得到不同的星系，无法做截图对比，也无法复现 bug。所有随机都应来自固定种子的哈希函数。

### 19.12 行星纹理是纯色

检查 `buildPlanetTexture` 的分支：地球走「大陆/海洋/极冠」模板，气态巨行星走「条带 + 涡旋」模板，类地行星走「陨击坑 + 噪声」模板。如果配色表里某个 id 写错，会落到 `default` 分支得到纯色。

检查 `texId` 缓存键：如果所有行星共用同一个缓存键，会得到同一张纹理；如果缓存键包含 `Math.random()`，则每次都是新纹理（性能灾难）。

### 19.13 自转方向错误

天文约定：从北天极俯视，行星逆时针自转（金星与天王星例外）。渲染中「北」是 +Y，因此 `uModel` 的旋转角度应该是**随时间增加**。如果发现某颗行星反转，检查数据表里是否有 `retrograde: true` 标记，以及应用的符号。

### 19.14 标签重叠或者乱跳

标签位置的解算是「投影到屏幕 → 尝试 7 个候选偏移 → 检查与已占用矩形的碰撞」。如果标签在相机缓慢移动时突然跳跃（从左边跳到右边），说明候选偏移的顺序不稳定或碰撞判定把自身算进去了。修复：每次重新布局时清空占用列表，并且严格按深度排序后依次放置。

### 19.15 移动端双指缩放失灵

- 必须 `touch-action: none`，否则浏览器会接管手势；
- 必须用 `pointerdown/pointermove/pointerup` 而不是 `touchstart`，或者两套都写。当前只用 Pointer Events，Safari 15.4+ 支持；
- 双指的「中点平移」与「距离缩放」必须在同一帧内一起计算，否则手感会「先缩放后平移」；
- `pointercancel` 必须处理，否则来电或通知弹出后手势状态会卡死（表现为之后所有拖动都是错的）。

## 第 20 章　交互场景走查

本章用「用户会做什么」的视角，把每一条路径走一遍，标出失败点。

### 20.1 场景一：第一次打开

1. 双击 `index.html`，浏览器打开本地文件；
2. 300ms 内出现加载层，文字为项目名；
3. 纹理生成开始，加载层显示进度，每 32 行更新一次；
4. 约 2.5 秒后纹理完成，WebGL 开始渲染；
5. 相机从略远处飞入默认位置（如果需要入场动画），或直接出现在默认位置；
6. 加载层淡出（`opacity` 过渡 400ms）；
7. 首次提示淡入：「拖动旋转 · 滚轮缩放 · Shift/右键拖动平移 · 按 ? 查看全部操作」，6 秒后自动淡出；
8. 标签逐个淡入。

失败点：

- **`file://` 下 ES module 被 CORS 拦截**：本项目用传统 `<script>`，无此问题。若将来引入模块，必须改为内联或提供本地服务器；
- **纹理生成失败**：`Uint8Array` 分配失败（内存不足），应捕获并降级到 512×512；
- **WebGL 不可用**：必须显示友好提示而不是白屏。

### 20.2 场景二：看星系全貌再靠近

1. 用户滚轮向前，相机推进；
2. `tRadius` 按 `exp` 曲线减小，每一格滚轮的视觉接近感一致；
3. 相机推进到 `radius ≤ 300` 时触发下钻；
4. 进入太阳系，相机自动补间到默认视角；
5. 系统标签出现。

失败点：

- **滚轮太快**：`wheel` 事件的 `deltaY` 在不同设备上是 1、3、100、120 不等。当前用 `exp(delta * 0.0014)`，对 120 的步长刚好合适；对触控板的 1 则极慢。改进方向：按 `deltaMode` 归一化（`deltaMode === 1` 时乘 16，`=== 2` 时乘 100）；
- **下钻瞬间丢失状态**：如果 `diveToSolar` 里没有保存银河的相机状态，返回时无法回到原位。

### 20.3 场景三：点空白处推进

1. 用户在旋臂上点了一下；
2. `galaxyPointAt` 求出交点 `P`；
3. `zoomToward` 把 `tTarget` 设为 `P`，`tRadius` 设为当前的 0.45 倍（双击 0.40 倍）；
4. 900ms 补间；
5. 到达后用户可以继续点击，逐级推进到 `diveR`。

失败点：

- **点在星系外**：交点超出 `radius * 1.15`，应当忽略（不推进），或者按「向该方向看」处理。当前是忽略；
- **点在核心**：目标半径急剧变小，但相机到目标的核心距离仍然很大，可能触发下钻条件。这是正确行为，但需要在 `diveToSolar` 时使用「目标点」作为下钻的中心，而不是固定原点。

### 20.4 场景四：点行星看历史

1. 在太阳系里点地球；
2. `pickAt` 命中地球（屏幕半径约 12px，热区 20px）；
3. `focusBody('earth')`：
   - 相机补间到地球上方偏 30°、距离 `视觉半径 × 6.5 + 4`；
   - 补间回调里打开信息面板；
4. 信息面板滑入（300ms），标题「地球」，正文包含简介与历史段落；
5. 用户可点关闭按钮或按 `Esc` 回到太阳系；
6. 自转继续（聚焦时减速到 0.35 倍，便于观察）。

失败点：

- **补间回调没触发**：见 19.8；
- **面板内容为空**：数据表的 `history` 字段缺失；
- **聚焦后无法退出**：`Esc` 的状态机判断写错（见 15.1 的分级规则）。

### 20.5 场景五：误触与打断

- 拖动到一半松手 → 相机继续按阻尼收敛到 `t*`，不突变；
- 补间进行中再次点击 → 新补间覆盖旧的，旧回调丢失（这是设计选择，避免回调堆积）；
- 补间进行中滚轮 → `tRadius` 被滚轮修改，补间仍在推进 `radius`，两者冲突。当前的处理是「滚轮立即取消补间」。**这是必须的**，否则用户会觉得滚轮没反应；
- `Esc` 连按 → 按优先级逐级退出，不能一次全退。

### 20.6 场景六：低性能设备

1. 首次运行，前 60 帧跳过采样；
2. 之后采样 120 帧的平均 `dt`；
3. `avgDt > 1/32`（低于 32fps）→ 降到「中」画质：`dpr` 1.25、粒子 0.6 倍、关暗尘；
4. 再采样 120 帧，仍低于 20fps → 降到「低」：`dpr` 1、粒子 0.35 倍、关星团、背景星减半；
5. 只降不升，避免在临界点来回震荡。

失败点：

- **降级后粒子数量变化导致视觉突变**：用「前缀抽样」而不是重新生成，粒子位置不变，只是少了后面的部分，视觉上像「变稀疏」而不是「换了一张图」；
- **`dpr` 改变后 canvas 尺寸未更新**：必须同时改 `canvas.width/height` 与 `gl.viewport`。

### 20.7 场景七：长时间停留

1. 星系持续自转（`spinPeriod = 180` 秒一圈，极慢）；
2. 粒子闪烁；
3. 标签位置随相机变化；
4. 内存不增长（所有缓冲在初始化时分配，无每帧分配）。

失败点：

- **每帧分配数组**：`M4.multiply` 用临时数组 `M4._t` 避免分配，但**不可重入**——如果在一个表达式里连续调用两次（如 `M4.multiply(M4.multiply(a,b), c)`），第二次会覆盖第一次的结果。这是本项目数学库的一个已知陷阱，写代码时必须「先算中间结果，再算最终结果」；
- **浮点累积**：`theta` 持续增加会损失精度，应在超过 `2π` 时取模。

## 第 21 章　性能剖析方法

### 21.1 为什么不能只测 FPS

单看 FPS 无法区分「GPU 瓶颈」与「CPU 瓶颈」，也无法定位到具体阶段。必须分阶段计时。

### 21.2 分阶段计时

在 `frame()` 内用 `performance.now()` 打点：

```js
var t0 = performance.now();
updateCamera(dt);
updateMeshes(dt);
var t1 = performance.now();
drawGalaxy();
var t2 = performance.now();
drawSolar();
var t3 = performance.now();
```

然后在调试浮层显示 `(t1-t0)`（JS 逻辑）、`(t2-t1)`、`(t3-t2)`。

要点：

- `gl` 调用是异步排队的，CPU 侧计时不含 GPU 执行时间。要看真实 GPU 耗时，必须用 `EXT_disjoint_timer_query`（WebGL1 扩展）或者在绘制后调用一次 `gl.finish()`（会严重拖慢，只用于测量）；
- 测量时关闭浏览器扩展与其他标签页；
- 无头模式的 SwiftShader 是纯软件渲染，帧耗时与真实 GPU 没有可比性，只能用来验证「逻辑是否正确」，不能用来判断「性能是否达标」。

### 21.3 关键指标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 首屏可见 | < 3.5 s | 从导航开始到第一帧含星系 |
| 纹理生成 | < 2.6 s | 逐批日志 |
| 稳定帧率 | ≥ 50 fps（中端独显） | 60 帧平均 |
| 每帧 JS | < 4 ms | `performance.now()` |
| 每帧绘制调用 | < 20 | 统计 `drawArrays`/`drawElements` |
| 内存 | < 120 MB | Chrome 任务管理器 |

### 21.4 粒子数量的实测影响

在本项目的实测中（340k 粒子、2048 纹理、1440×810）：

- 粒子数对帧率的影响近似线性，但斜率取决于「屏幕覆盖面积」：粒子在远处聚成光斑时，overdraw 才是主要成本，而不是顶点数；
- `gl_PointSize` 从 56 降到 32 可以显著减少近景的填充率压力，代价是近处粒子看起来「不够大」；
- 盘面纹理是一张全屏四边形，成本很低，但它必须最后绘制吗？**不是**——必须最先绘制，因为它是「底」，粒子叠加在其上，暗尘在其上，任何顺序错误都会导致遮挡。

### 21.5 自适应画质的正确做法

不要用「帧率低于阈值就立刻降级」，因为帧率本身有抖动（切标签页、GC、系统通知）。正确做法：

1. 预热期（60 帧）不采样；
2. 采样窗口（120 帧）取平均；
3. 用**中位数**而不是平均值更稳健；
4. 每次降级后重新进入预热期，避免连续降级；
5. 只降不升（或者升级需要连续 3 个窗口都优良，P1 不做）。

### 21.6 内存

所有 `Float32Array`/`Uint8Array` 都应在初始化时一次分配：

- 340k 粒子 × (pos 3 + color 3 + size 1 + seed 1) × 4 字节 ≈ 10.9 MB；
- 64k 暗尘 ≈ 2 MB；
- 12k 背景星 ≈ 0.4 MB；
- 盘面纹理 2048² × 4 × 3 张 ≈ 50 MB（GPU 侧）；
- 行星纹理 512² × 4 × 9 ≈ 9 MB。

总计约 75 MB，在 120 MB 预算内。**纹理是内存大户**，临时生成的 `Uint8Array` 在上传 GPU 后必须置空让 GC 回收，否则峰值会翻倍。

### 21.7 绘制调用的组织

一个星系 34 万粒子如果每颗都单独调用一次绘制，即使帧率只有 1fps 也来不及。本项目的做法是把所有粒子塞进同一组顶点缓冲，用一次 `gl.drawArrays(gl.POINTS, 0, count)` 画完。这带来三个约束：

1. **所有粒子必须共享同一套 uniform**。如果想让「核球粒子」和「旋臂粒子」用不同的衰减系数，不能分成两次绘制来分别设置 uniform（那会翻倍绘制调用），而应该把差异编码进顶点属性——本项目用 `aSize` 与 `aColor` 承担全部差异；
2. **降采样必须靠前缀**。因为每颗粒子的属性是独立生成的随机值，数组的前 N 个元素天然构成一个均匀子集，所以自适应画质只需改 `count`，不需要重建缓冲。这条性质很重要，它让降级与恢复都不产生卡顿；
3. **顶点缓冲只上传一次**。`gl.STATIC_DRAW` 提示驱动「不会再改」，驱动可以把它放到更快的显存里。如果每次自转都重算粒子位置，就得用 `gl.DYNAMIC_DRAW` 并每帧上传 11MB，性能会塌方。

自转因此做在 `uModel` 矩阵上，而不是顶点数据上。代价是所有粒子绕同一根轴刚性旋转，无法表现「内圈转得快、外圈转得慢」的较差自转。真实星系确实有较差自转，但在这个尺度下，刚性旋转与较差自转的视觉差异要几万年才看得出来——不值得为它多付每帧 11MB 的上传成本。

其他绘制批次：

- 盘面纹理：一个四边形，一次 `drawElements`；
- 暗尘：一个四边形，一次；必须在盘面之后、粒子之前；
- 背景星：一次，与星系粒子共用着色器，靠 `uFixedSize > 0` 分支走固定像素尺寸；
- 行星与光环：每颗行星 1–2 次，共约 12 次；
- 轨道线：合并成一个缓冲，一次 `drawArrays(LINES)`；
- 标签：走 DOM，不占绘制调用。

总计约 18 次绘制调用，符合第 21.3 节「每帧 < 20」的预算。如果将来加入小行星带或卫星，应优先合并到已有批次（例如把小行星带并入粒子着色器，用 `aSize` 区分），而不是新增绘制调用。

## 第 22 章　天文背景知识

本章写给「要往场景里加东西」的人。不需要天文专业背景，但需要知道哪些视觉约定是**不能违反**的，否则画面会立刻显得假。

### 22.1 银河系的真实结构

银河系是一个**棒旋星系**（barred spiral），不是完美的「风车」。主要成分：

| 结构 | 真实尺度 | 本项目表现 |
|---|---|---|
| 银心（中心黑洞） | 极大质量，但视觉上不可见 | 核心最亮处 |
| 核球（bulge） | 直径约 1 万光年 | 拉长的椭球，暖黄色 |
| 棒（bar） | 长约 2.5 万光年 | 核球的 X 方向拉长 1.34 |
| 旋臂（arms） | 4 条主臂 + 若干次臂 | 4 条对数螺旋 |
| 银盘（disk） | 直径约 10 万光年，厚度约 1000 光年 | 半径 2500 的薄盘，Y 方向压扁 |
| 银晕（halo） | 球状，包含球状星团与暗物质 | 稀疏粒子 + 球形分布 |
| 尘带（dust lane） | 沿旋臂内侧的暗带 | 减法混合的暗尘纹理 |

**关键比例**：银盘的直径与厚度之比约 100:1。本项目为了让盘面在斜视时有体积感，实际压扁比例比真实值「厚」一些（Y 方向按 0.5 压扁，而不是 0.01）。这是可视化惯例：如果严格按 1:100，从侧面看星系就是一条线，什么都看不出来。

### 22.2 密度波与旋臂

真实旋臂**不是物质聚集的固定结构**，而是「密度波」——恒星在轨道上运行时穿过旋臂区域会减速、聚集，就像高速公路上的堵车点会保持位置而车辆不断通过。

可视化上不需要模拟密度波，但需要遵守两个结果：

1. **旋臂有明确的锐利内缘与弥散外缘**（冲击波压缩的前沿在内侧）；
2. **暗尘集中在旋臂的内侧（凹侧）**，因为那里是气体密度最高的地方。

本项目用「暗带相位超前 0.95 弧度」来实现第 2 点。

### 22.3 恒星颜色与温度

恒星的颜色由表面温度决定（黑体辐射）：

| 光谱型 | 温度 | 颜色 | 占比（近似） |
|---|---|---|---|
| O | > 30000 K | 蓝紫 | 极稀有 |
| B | 10000–30000 K | 蓝白 | 少 |
| A | 7500–10000 K | 白 | 少 |
| F | 6000–7500 K | 黄白 | 多 |
| G | 5200–6000 K | 黄（太阳） | 多 |
| K | 3700–5200 K | 橙 | 很多 |
| M | < 3700 K | 红 | 最多 |

**重要事实**：数量最多的恒星是暗弱的红矮星（M 型），但它们在星系照片里几乎看不见；我们看到的光主要来自少数极亮的蓝巨星与黄白主序星。因此可视化应该「少而亮的蓝星 + 多而暗的红星」，而不是均匀分布。

本项目的做法：3% 的粒子标记为蓝巨星，尺寸乘 3.4，颜色偏蓝；核球内 10% 偏红；旋臂中另有 3.2% 粉色、2.4% 青色、1.2% 靛紫的星云色点缀。

### 22.4 尘埃与红化

星际尘埃会吸收蓝光、散射红光，导致远处的星光「偏红」，这在专业上叫「星际红化」。可视化的对应做法：

- 暗尘带不要做成纯黑的洞，而应该是「降低亮度 + 略微偏红」；
- 星系背面的恒星如果被尘带遮挡，应该变暗而不是消失。

本项目当前用纯减法实现暗尘（只降低亮度，不改色），这是简化。如果要做得更真实，可以把减法换成「乘以一个偏红的透射率」。

### 22.5 哈勃分类

哈勃序列：E（椭圆）→ S0（透镜）→ Sa/Sb/Sc（旋涡，臂从紧到松）→ SBa/SBb/SBc（棒旋）→ Irr（不规则）。

银河系接近 **SBbc**：有棒，旋臂中等松散。如果要加「其他星系」作为背景或切换目标，可以按这个分类准备不同参数：

- E0–E7：无旋臂，按轴比从圆到椭圆；
- Sa：臂紧绕，核球大；
- Sc：臂松散，核球小，有大量恒星形成区（粉色团块）；
- Irr：无结构，随机分布。

### 22.6 太阳系尺度与压缩

真实尺度：

| 天体 | 轨道半长轴（AU） | 半径（km） |
|---|---|---|
| 水星 | 0.387 | 2440 |
| 金星 | 0.723 | 6052 |
| 地球 | 1.000 | 6371 |
| 火星 | 1.524 | 3390 |
| 木星 | 5.203 | 69911 |
| 土星 | 9.537 | 58232 |
| 天王星 | 19.19 | 25362 |
| 海王星 | 30.07 | 24622 |

**问题**：如果按线性比例，地球半径是 1 单位时，海王星的轨道半径是 30 单位，而屏幕只有几十单位高，根本看不全；同时木星半径会是地球的 11 倍，视觉上压倒一切。

**本项目的压缩**：

```
orbitRadius = 30 * au^0.55
planetRadius = 1.9 * (d / 12742)^0.38
```

验证：

| 天体 | AU | 轨道半径（压缩后） | 直径比 | 行星半径（压缩后） |
|---|---|---|---|---|
| 水星 | 0.387 | 30 × 0.588 = 17.6 | 0.383 | 1.9 × 0.685 = 1.30 |
| 地球 | 1.000 | 30.0 | 1.000 | 1.90 |
| 木星 | 5.203 | 30 × 2.50 = 75.1 | 10.97 | 1.9 × 2.44 = 4.64 |
| 海王星 | 30.07 | 30 × 6.58 = 197 | 3.86 | 1.9 × 1.72 = 3.27 |

结果：**轨道跨度从 30 倍压到 6.6 倍**，**行星半径跨度从 11 倍压到 2.4 倍**。既保留了「外行星更远」「木星最大」的直觉，又能在同一屏里看清。

### 22.7 公转与自转的方向

- 所有行星**从北天极俯视逆时针公转**（与太阳自转方向一致，来自原始星云的角动量）；
- 除金星（逆向自转，周期 243 天）与天王星（轴倾角 98°，几乎躺倒）外，其他行星都是逆时针自转；
- 自转周期差异巨大：木星 9.9 小时，金星 243 天。

本项目为了「看得见自转」，把自转速度统一压缩到 1–3 秒一圈，**不真实但必要**。这属于可视化惯例，必须在文档与 UI 中说明，不能让观众以为这是真实速度。

### 22.8 潮汐锁定与轨道倾角

- 月球被地球潮汐锁定，永远同一面朝向地球；
- 行星轨道有微小倾角（相对黄道，最大的是水星 7°），本项目把轨道画在同一个平面上，是简化；
- 土星环位于赤道面，因此随轴倾角 26.7° 倾斜；
- 天王星的环几乎垂直，因为它自身躺倒。

本项目对土星环与天王星环都做了倾斜，这是仅有的两处「环」的细节。

### 22.9 距离与「看得见」的悖论

真实宇宙中，恒星之间的距离是星球直径的千万倍以上。如果做一个「从地面飞到比邻星」的动画，99.999% 的时间都是空的。

**可视化的核心妥协**：把「尺度」与「距离」分开压缩。这正是本项目的「双层结构」——银河层用一套比例，太阳系层用另一套，中间用淡入淡出衔接。这不是偷懒，而是唯一可行的方案。

### 22.10 加新天体时的检查清单

1. 轨道半径是否落在现有范围内？超出会飞出可视区；
2. 行星半径压缩后是否与其他行星区分？太小会看不见；
3. 纹理模板是否匹配？（气态 → 条带；岩质 → 陨击坑；冰质 → 平滑渐变）
4. 自转方向是否正确？是否有 `retrograde` 标记？
5. 轴倾角是否正确？影响光环方向；
6. 历史文本是否要加？加多少字？
7. 是否影响标签布局？（新天体必须有中文名与英文名）
8. 是否影响相机聚焦距离的计算？（半径变了，`×6.5` 的系数是否仍合适）

## 第 23 章　数据表规范

`BODIES` 数组是唯一的数据来源。任何新天体都必须按以下字段填写，缺字段会在运行时崩溃或显示为 `undefined`。

### 23.1 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 小写英文，唯一，用于深链接与拾取 |
| `zh` | string | 是 | 中文名，标签与面板标题 |
| `en` | string | 是 | 英文名，标签副标题 |
| `radiusKm` | number | 是 | 真实半径，用于压缩计算 |
| `au` | number | 是 | 轨道半长轴，单位 AU |
| `orbitDays` | number | 是 | 公转周期，单位地球日 |
| `spinHours` | number | 是 | 自转周期，单位小时；负值表示逆向 |
| `tilt` | number | 否 | 轴倾角（度），默认 0 |
| `color` | string | 是 | 主色，纹理回退用 |
| `color2` | string | 是 | 次色（条带/高地） |
| `tex` | string | 是 | 纹理模板：`rocky`/`gas`/`earth`/`ice` |
| `ring` | object | 否 | `{inner, outer, opacity}`，以行星半径为倍数 |
| `moons` | number | 否 | 卫星数量，仅用于信息面板展示 |
| `dayLen` | string | 否 | 一天长度的人类可读文本 |
| `yearLen` | string | 否 | 一年长度的人类可读文本 |
| `gravity` | string | 否 | 表面重力，人类可读 |
| `temp` | string | 否 | 平均/表面温度 |
| `intro` | string | 是 | 2–3 句简介，面板首段 |
| `history` | string | 是 | 历史与人文，200–400 字，按段落分隔 |

### 23.2 太阳的例外

太阳在 `BODIES` 里但不在 `PLANET_ORBITS` 里：`au = 0`，不在轨道列表中生成轨道线，纹理为 `star` 模板（自发光），`uEmissive = 1`。

### 23.3 `history` 字段的写作要求

1. **时间线优先**：从古代观测写到现代探测，按时间顺序；
2. **包含人类文化**：命名由来、神话、文学、艺术中的出现；
3. **包含关键科学节点**：第一次望远镜观测、探测器任务、重大发现；
4. **避免虚构**：不确定的内容宁可省略；
5. **200–400 字**：太短显得敷衍，太长面板滚动困难；
6. **段落之间用 `\n\n` 分隔**：面板用 `white-space: pre-wrap` 渲染。

示例（地球，节选）：

> 人类对地球形状的认识经历了漫长过程。古希腊的埃拉托色尼在公元前 3 世纪用日影测量出地球周长，误差不到 15%。1519 年麦哲伦船队启航，用三年时间完成首次环球航行，从实践上证明了地球是球体。
>
> 1957 年苏联发射第一颗人造卫星，1961 年加加林成为第一个进入太空的人。1968 年阿波罗 8 号在绕月轨道上拍下「地球升起」，这张照片改变了人类看待自身星球的方式。1972 年阿波罗 17 号的「蓝色弹珠」成为流传最广的地球影像。

### 23.4 标签命名约定

- 中文名 2–4 个字最佳，超过 5 个字在小屏幕上会被截断；
- 英文名首字母大写，不使用全大写（全大写会显得像缩写，读者会误以为是术语）；
- 不要用「XX星」这样的泛称作为唯一名字，必须有专属名。

### 23.5 校验

新增或修改 `BODIES` 后必须运行校验脚本（`tools/smoke_test.py` 中含静态检查），检查：

- `id` 唯一；
- 所有必填字段存在且类型正确；
- `au` 严格递增（若不递增，轨道线绘制顺序会错）；
- `radiusKm > 0`；
- `history` 长度在 150–800 字符之间；
- 深链接用的 `id` 不含空格与中文。

## 第 25 章　常见问题

**问：为什么不用 Three.js？**
答：第一，单文件约束下引入 600KB 的库会让文件膨胀，且需要额外处理 `file://` 下的加载；第二，本项目只用到「矩阵 + 点精灵 + 简单网格」，手写代码约 300 行，比调试一个库的子集更直接；第三，零依赖意味着十年后打开仍然能跑。

**问：为什么纹理是程序化生成的？**
答：避免外部图片依赖（`file://` 下加载图片有跨域限制，且会增加体积），同时可以随参数调整。代价是首次启动约 2.5 秒。

**问：能不能加载真实的银河系照片？**
答：可以，但会失去「可缩放」的特性——照片放大就是模糊。程序化生成在任意缩放下都有细节。折中方案是用真实照片作为远景底图，Near 时切换到程序化，P2。

**问：为什么放大到行星之后看不到其他行星？**
答：聚焦时相机距离是行星半径的 6.5 倍，其他行星在几十到上百单位外，被视锥剔除或太小。这是正确的（就像站在地球上抬头找不到火星）。

**问：能加真实的星表数据吗？**
答：可以，但会极大增加文件体积（依巴谷星表约 10 万颗）。当前用程序化分布 + 少量「已知结构」（旋臂、核球、球状星团）已经足够。

**问：为什么不支持 VR？**
答：VR 需要 WebXR，与「单文件、双击即用」的约束冲突（需要安全上下文）。P3 可考虑。

**问：手机上很卡怎么办？**
答：首次自动降级。若仍卡，可在控制台手动设置 `quality.level = 'low'`，或减少 `CFG.galaxy.particles`。

**问：文字是英文？**
答：界面默认中文。如果要英文，需要一份完整的 `i18n` 表，P2。

**问：双击 `index.html` 打不开？**
答：极少数环境（某些 Electron 封装、企业策略）禁止 `file://` 下的 WebGL。用 `python -m http.server` 起一个本地服务器访问 `http://localhost:8000`。

**问：为什么星系在转但行星不动？**
答：星系的「转速」是整体旋转矩阵，成本几乎为零；行星公转需要每帧更新位置，且真实周期差异巨大，统一压缩后某些行星看起来是静止的。当前只对自转做了压缩，公转保持真实比例换算。

### 用例 01　冷启动首屏

- **前置**：浏览器缓存已清空，`file://` 打开 `index.html`；
- **步骤**：打开页面，不做任何操作，等待 5 秒；
- **预期**：加载层在 3.5 秒内消失；画面出现可辨认的四条旋臂；中央有暖色核球；背景有稀疏星点；左侧品牌文字、右下角提示均已就位；
- **判定**：截图后目视。「可辨认的旋臂」的标准是：不看文档也知道这是螺旋星系，而不是一团随机噪点。

### 用例 02　默认相机参数

- **前置**：冷启动完成；
- **步骤**：在控制台读取 `cam.radius`、`cam.phi`、`cam.theta`；
- **预期**：`radius ≈ 3600`、`phi ≈ 1.107`、`theta ≈ 1.571`（误差 ±0.02）；
- **判定**：数值比较。若 `radius` 明显小于 3000，说明入场补间没有收尾；若 `phi` 偏离，说明阻尼还没收敛（应等待 2 秒后再读）。

### 用例 03　旋转拖动

- **步骤**：在画布中央按下左键，水平拖动 200px 后松开；
- **预期**：星系绕竖直轴转过约 `200 × 0.0042 = 0.84` 弧度；拖动过程中画面跟手，不出现滞后超过 0.2 秒的延迟；松手后不再继续旋转；
- **判定**：读取 `cam.tTheta` 与拖前的差值，误差 ±0.05 弧度。

### 用例 04　垂直拖动的极点夹紧

- **步骤**：按住左键持续向上拖动 2000px；
- **预期**：相机从上方俯视逐渐转到底部视角，但**不会翻转**；`phi` 最终停在 0.08；
- **判定**：读取 `cam.phi`，断言 `cam.phi >= 0.08 - 1e-6`。反向拖到底应停在 `π - 0.08`。

### 用例 05　右键平移

- **步骤**：按住右键（或中键，或 Shift + 左键）向右拖动 150px；
- **预期**：注视点沿相机右方向移动，屏幕上的星系整体向右移动约 150px；平移过程中相机姿态（旋转角）不变；
- **判定**：读取 `cam.target` 前后差值，投影到相机右向量上的长度应为 `150 × k`，其中 `k = 2·tan(fov/2)·radius/screenH`，允许 ±10% 误差。

### 用例 06　平移的平面限制

- **步骤**：按住 Shift 连续向左下拖动，直到画面里看不到星系；
- **预期**：注视点被限制在银盘平面内，且距原点不超过 `radius × 1.15`；不能把相机拖到「星系外面无限远」；
- **判定**：读取 `cam.target`，断言 `target.y === 0` 且 `hypot(x, z) <= 2875`（2500 × 1.15）。

### 用例 07　滚轮缩放曲线

- **步骤**：连续向前滚动 10 格，每格间隔 100ms；
- **预期**：每格的视觉接近比例一致（指数缩放），总缩放倍数约为 `exp(10 × 120 × 0.0014) ≈ 5.3`；
- **判定**：读 `cam.tRadius`，断言 `tRadius ≈ 3600 / 5.3 ≈ 679`（误差 ±15%）。若某个方向快到第二格就穿模，说明指数系数被改大。

### 用例 08　缩放下限与下钻

- **步骤**：在银河层持续向前滚动，直到状态改变；
- **预期**：`tRadius` 降到 300 时触发 `diveToSolar()`；状态变为 `TRANSITION`；约 1.7 秒后变为 `SOLAR_IDLE`；相机到达 `radius ≈ 360`；
- **判定**：观察 `state` 变量与 `cam.radius`。若滚到底仍停在银河层，检查 `diveR` 与 `minR` 的先后顺序：`minR(250) < diveR(300)` 是正确关系。

### 用例 09　点击空白推进

- **步骤**：在银河层点一下旋臂上的空白处；
- **预期**：相机朝该点方向推进；注视点变为点击处的世界坐标（`y = 0`）；`radius` 缩小到点击前的 0.45 倍；补间 900ms；推进后点击处仍在屏幕中央附近；
- **判定**：读取 `cam.tTarget` 与 `cam.tRadius`。若 `tTarget` 全是 0，说明射线求交失败。

### 用例 10　点击星系外

- **步骤**：把相机拉到很远（`radius = 7000`），点击画面四个角的空白；
- **预期**：**不发生任何位移**，不触发下钻，UI 不报错；
- **判定**：`cam.tTarget` 与 `cam.tRadius` 在点击前后完全一致。

### 用例 11　点击行星聚焦

- **步骤**：进入太阳系，点击地球；
- **预期**：状态变为 `PLANET_FOCUS`，`focusedId === 'earth'`；相机在 1.2 秒内移到地球上方偏 30°、距离 `1.9 × 6.5 + 4 = 16.35`；信息面板打开，标题为「地球」；
- **判定**：读取 `focusedId`、`cam.radius`、`#infoZh.textContent`。

### 用例 12　历史内容

- **步骤**：在地球聚焦态，读取 `#histText`；
- **预期**：内容长度在 150–800 字符之间，包含至少两个段落（`\n\n` 出现至少一次），不含 `undefined`；
- **判定**：断言 `text.length > 150 && text.indexOf('undefined') < 0`。

### 用例 13　Esc 分级退出

- **步骤**：在行星聚焦态按一次 `Esc`；
- **预期**：回到太阳系默认视角，面板关闭，`focusedId === null`；
- **步骤**：再按一次 `Esc`；
- **预期**：回到银河层；
- **步骤**：再按一次 `Esc`；
- **预期**：回到银河默认视角；
- **判定**：每步读取 `state`，断言依次为 `SOLAR_IDLE`、`GALAXY_IDLE`、`GALAXY_IDLE`（角度归位）。

### 用例 14　键盘平移与缩放

- **步骤**：按住 `W` 键 1 秒；
- **预期**：注视点沿「相机前方投影到银盘」的方向移动约 520px 对应的世界距离（`panSpeed = 520` CSS px/s）；松开即停；
- **步骤**：按 `+` 三次、`-` 一次；
- **预期**：`tRadius` 依次乘 0.85、0.85、0.85、1.18，净倍数 0.725；
- **判定**：数值断言。注意 `+` 与 `-` 必须区分主键盘与数字键盘（`key === '+'` 与 `key === '='` 在美式键盘上分别是 Shift 与不按 Shift）。

### 用例 15　快捷键不误伤输入框

- **前置**：页面上没有输入框（P1 无表单），但需防御未来的搜索框；
- **步骤**：在 `document.activeElement` 为 `input` 或 `textarea` 时按 `R`；
- **预期**：不触发重置视角；
- **判定**：断言 `keydown` 处理函数在开头有 `if (/^(INPUT|TEXTAREA)$/.test(e.target.tagName)) return;`。

### 用例 16　双击

- **步骤**：在银河层快速双击（间隔 < 280ms、位移 < 8px）；
- **预期**：触发一次 `zoomToward`，步长 0.40 倍（比单击的 0.45 更近）；**不触发两次单击**；
- **判定**：读取 `cam.tRadius`，断言是单击前的 0.40 倍（±2%）。若变成 0.45² = 0.2025 倍，说明单击逻辑没有防抖。

### 用例 17　深链接

- **步骤**：打开 `index.html#body/mars`；
- **预期**：跳过入场动画，直接进入火星聚焦态，面板打开；
- **步骤**：打开 `index.html#galaxy/r1200`；
- **预期**：银河层，`radius ≈ 1200`；
- **步骤**：打开 `index.html#body/nosuch`；
- **预期**：静默忽略，落在默认银河视角，控制台无错误；
- **判定**：读取状态与 `cam.radius`。

### 用例 18　截图

- **步骤**：点击工具栏相机按钮；
- **预期**：1 秒内下载一张 PNG，文件名形如 `milkyway-20261109-153012.png`；图像内容与当前画面一致（不含 DOM 面板）；
- **判定**：检查下载目录与图片尺寸。若图片是黑屏，说明 `toBlob` 在 `preserveDrawingBuffer = false` 下的时机错误——必须在同一帧 `drawArrays` 之后、浏览器缓冲交换之前调用。

### 用例 19　自适应画质

- **步骤**：用 Chrome DevTools 的 CPU 节流 6× 后刷新；
- **预期**：约 3 秒后 `quality.level` 从 `high` 降到 `mid`；粒子绘制数量变为 `floor(340000 × 0.6)`；画面仍可辨认；
- **判定**：读取 `quality.level` 与 `gl.getParameter` 无关的绘制计数变量。**注意**：降级只应发生一次，不应在 `mid` 与 `low` 之间反复跳。

### 用例 20　窗口尺寸变化

- **步骤**：把窗口从 1440×810 拖到 800×600，再拖回；
- **预期**：`canvas.width/height` 随 DPR 更新；`gl.viewport` 同步；画面不变形（球仍是圆）；标签位置正确；无 `NaN`；
- **判定**：截图对比宽高比。若球变成椭圆，说明只更新了 `canvas` 尺寸而没有更新投影矩阵的 `aspect`。

### 用例 21　触摸手势

- **前置**：Chrome DevTools 设备模拟（iPhone 12）；
- **步骤**：单指拖动 200px；
- **预期**：旋转，且页面不滚动；
- **步骤**：双指从相距 100px 张开到 200px；
- **预期**：放大 2 倍；双指中点位置保持不变；
- **步骤**：双指同时移动（距离不变）；
- **预期**：平移；
- **判定**：读取 `cam.tRadius` 与 `cam.tTarget`。若缩放倍数不是 2.0，检查是否把「距离比」用反（应为 `d0/d1` 而不是 `d1/d0`）。

### 用例 22　长时间稳定性（5 分钟）

- **步骤**：打开页面，让它自己运行 5 分钟；

- **判定**：Chrome 任务管理器每 30 秒记录一次内存。若内存线性增长，查找每帧分配的数组（常见于 `map`/`filter`/`slice`）。

### 用例 23　上下文丢失恢复

- **前置**：可用 `WEBGL_lose_context` 扩展模拟；
- **步骤**：调用 `gl.getExtension('WEBGL_lose_context').loseContext()`；

- **判定**：在不支持自动恢复的 P1 版本中，至少应显示提示而不是白屏。

### 用例 24　无 WebGL 环境

- **前置**：禁用 WebGL（`chrome://flags` 关闭硬件加速并禁用软件回退）；
- **步骤**：打开页面；
- **预期**：显示中文说明「当前浏览器不支持 WebGL」+ 建议（更新浏览器 / 启用硬件加速）；不出现白屏或英文报错；

### 用例 25　文件完整性

- **步骤**：断网后双击打开；
- **预期**：完全正常；DevTools 的 Network 面板无任何请求（除了文件本身）；
- **判定**：Network 面板应为空。若出现请求，说明引入了外部资源，违反零依赖约束。

### 用例 26　静态检查

- **步骤**：抽出 `<script>` 内容保存为 `_check.js`，执行 `node --check _check.js`；
- **预期**：输出为空、退出码 0；
- **判定**：这是每次改动后**必须**执行的一步，它能在 100ms 内发现语法错误，比打开浏览器快一个数量级。

### 27.2 自动化取舍

P1 阶段不引入测试框架，原因有三：

1. 单文件、无构建，引入 Jest/Playwright 会打破「双击即用」的开发体验；
2. 大部分断言依赖 WebGL 渲染结果，无法在 Node 中断言；
3. 无头 Chrome + Swiftshader 的时序不可靠（见 19.10），自动化截图比对会产生大量假阳性。

替代方案是「探针 + 确定性单帧推进」：在页面里注入一段调试脚本，用固定帧号执行操作、直接读全局变量、把结果写进 DOM 浮层，再用截图读回。这套方法在本项目已经验证可行，成本远低于搭建完整测试框架，且不污染生产代码（探针脚本以 `_` 开头，被 `.gitignore` 排除）。

当 P2 引入真实的构建流程后，再考虑把「数值断言」部分迁移到 Puppeteer，而「视觉断言」仍保留人工三图对比。

### 27.4 缺陷分级与处理时限

不是所有问题都值得在发版前修。按下面的标准分级，避免把时间花在无意义的细节上。

**P0　阻断级**——必须修完才能发版：

- 打开是白屏、黑屏，或整页报错；
- 交互完全失效（点了没反应、拖不动）；
- 画面出现 `NaN` 导致几何体消失；
- 控制台有未捕获异常；
- 页面需要联网才能运行，或出现外部请求；
- 出现凭据、个人数据、内部资料。

**P1　严重级**——应在本次发版前修复；如果确实来不及，必须在 README 的「已知问题」中列出：

- 某一个交互方向相反或失效（例如右键不能平移）；
- 聚焦后无法退出；
- 在主流浏览器（Chrome、Edge、Safari 最新版）上出现可见的渲染错误；
- 首屏耗时超过 8 秒；
- 内存持续增长。

**P2　一般级**——可以排到下一次迭代：

- 标签偶尔重叠；
- 某个角度的暗环、条纹、色带；
- 键盘快捷键与浏览器默认行为冲突（在不影响主流程的情况下）；
- 移动端某个手势不灵敏。

**P3　体验级**——记录到 issue 列表，按兴趣处理：

- 「希望能加某颗行星」「希望能改颜色」；
- 动画时长的主观偏好；
- 文案措辞。

判级时用一句话自问：**「如果用户只看一眼就关掉，这个问题会不会让这一眼失败？」** 会 → P0 或 P1；不会 → P2 或 P3。这条准则能挡掉绝大部分「凭感觉想改」的冲动。

### 27.5 发版前的最后五分钟

在点击推送之前，用固定的顺序做这五件事，顺序不能颠倒：

1. 跑一遍用例 26，确认语法；
2. 打开页面，从银河一路点到地球，确认主路径通畅；
3. 打开 DevTools 的 Network 面板，确认没有任何请求；
4. 搜索代码里是否残留 `console.log`、`debugger`、`TODO`、`FIXME`；
5. `git status` 确认没有把 `_` 开头的调试文件、截图、探针脚本带进提交。

前四件是质量，最后一件是安全——一旦把调试文件推上去，它就会永久留在历史里，即使后来删除也能被翻出来。

## 第 28 章　禁止事项

1. **禁止**引入任何外部依赖，包括「只有 2KB 的小库」；
2. **禁止**把项目拆成多个 JS 文件（P3 增强版除外）；
3. **禁止**用在加载期间使用全屏黑色遮罩做层切换；
4. **禁止**在纹理生成路径中使用 `Math.random()`（破坏可复现性）；
5. **禁止**在 `pointerup` 里只判断 `e.button`（触摸事件的 button 为 0 或 undefined，必须兼容）；
6. **禁止**忽略 `FUNC_REVERSE_SUBTRACT` 的状态恢复；
7. **禁止**把 `state` 判断写成字符串字面量（必须用 `ST` 常量）；
8. **禁止**在交付文件中留下调试浮层、注释掉的旧代码、`debugger`；
9. **禁止**未经核实编造天文数据；
10. **禁止**把本项目与「工程机器人知识库」等内部资料混在一个仓库或一次发布中。
